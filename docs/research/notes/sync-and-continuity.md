## 1. Architectural options and trade-offs for a single user

### Takeaway
For one person, "bring-your-own synced folder" is the only option with zero server, zero recurring cost and near-zero code on **desktop** (Windows/macOS), but it does **not** extend cleanly to phones: no mainstream cloud keeps a real two-way-synced folder on Android or iOS that a third-party app can open as a tree, so mobile needs either a direct cloud API client inside the app, a companion sync tool (Syncthing-Fork, FolderSync-style apps, Möbius Sync, Working Copy), or iCloud Drive (Apple only). CRDT/sync-engine stacks and an app-owned E2EE service are technically mature in 2026 but are solving multi-writer real-time problems this user does not have; they are worth using only for the small **app-state** layer, not for the files.

### Cited Findings

#### (a) Bring-your-own cloud folder (provider does the sync)

**Windows (desktop)**
- OneDrive Files On-Demand files exist in three states (online-only, locally available, always available/pinned), each mapped to file attributes that can be queried and set (e.g. `attrib +P/-P/+U`). [S] — [Microsoft Learn: Query and set Files On-Demand states in Windows](https://learn.microsoft.com/en-us/onedrive/files-on-demand-windows)
- Placeholder files carry `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` or `FILE_ATTRIBUTE_RECALL_ON_OPEN`; applications and filters are advised not to open/read such files unless necessary, because reading triggers a download ("recall"). A plain `ls`/`stat` implementation that opens files was reported to cause mass downloads from OneDrive. [S] — [Cygwin mailing list, Mar 2024](https://sourceware.org/pipermail/cygwin/2024-March/255623.html); the flag is set by the cloud filter driver (CldFlt), not by ordinary apps [S] — [OSR forum](https://community.osr.com/discussion/comment/304589)
- iCloud for Windows also projects iCloud Drive into Explorer, but Obsidian's help is quoted as warning that "iCloud Drive on Windows may lead to file duplication or corruption" and lists only macOS/iOS/iPadOS as recommended for iCloud; many user threads (2021–2025) report "(1)", "(2)" duplicates, files stuck "sync pending", and one thread titled "Spontaneous deletion of the currently edited .md file (Windows 11 + iCloud)". [S] — [Obsidian forum: iCloud on Windows creates duplicate files](https://forum.obsidian.md/t/icloud-on-windows-creates-duplicate-files/48358), [Obsidian forum: spontaneous deletion](https://forum.obsidian.md/t/spontaneous-deletion-of-the-currently-edited-md-file-windows-11-icloud/111506), [2,000+ duplicates of workspace file](https://forum.obsidian.md/t/over-2-000-duplicates-of-the-workspace-file-under-the-obsidian-folder/29965)
- Google Drive for desktop offers **stream** (files stay in cloud, fetched on demand) and **mirror** (full local copy, offline by default). Google says write-heavy apps are faster with mirroring; offline files in stream mode are only reachable while Drive for desktop is running and signed in; "some applications use a combination of APIs that make files difficult to stream". When local content differs from cloud during a mode switch, Drive "keeps both". [S] — [Google Drive Help: Stream & mirror files](https://support.google.com/drive/answer/13401938?hl=en), [Customize Drive for desktop settings](https://support.google.com/drive/answer/13470231?hl=en)
- Dropbox desktop keeps a real local folder (optionally with online-only files) and ignores common editor temp/lock files (names starting `~$` or `.~`, `.tmp`, `desktop.ini`, etc.), which matters for Office-style lock files. [BK] — [Dropbox Help: files that don't sync](https://help.dropbox.com/sync/files-not-syncing)

**macOS (desktop)**
- OneDrive on macOS uses Apple's File Provider platform; Files On-Demand states are queryable/settable similarly to Windows. [S] — [Microsoft Learn: Files On-Demand on Mac](https://learn.microsoft.com/en-us/onedrive/files-on-demand-mac)
- Since macOS 12.3 the third-party clouds (OneDrive, Dropbox, Google Drive streaming) live under `~/Library/CloudStorage/` as File Provider domains with "dataless" files that materialise on first read; apps should use `NSFileCoordinator` and should not enumerate-and-read everything. [BK] — [Apple: File Provider](https://developer.apple.com/documentation/fileprovider), [Microsoft Tech Community: Inside the new Files On-Demand experience on macOS](https://techcommunity.microsoft.com/blog/onedriveblog/inside-the-new-files-on-demand-experience-on-macos/3058922)
- iCloud Drive is first-class on macOS; conflicts are surfaced to apps through `NSFileVersion` (a "conflict winner" is chosen as current; losers are listed by `unresolvedConflictVersionsOfItem(at:)`); same-name new-file collisions get a "bounced" name. A 2025 Apple forum thread questions whether the winner is consistent across devices after simultaneous edits. [S] — [Apple TN2336](https://developer.apple.com/library/content/technotes/tn2336/_index.html), [Apple Developer Forums 804253](https://developer.apple.com/forums/thread/804253)

**Android**
- Android's Storage Access Framework lets an app talk to any `DocumentsProvider` (local or cloud). `ACTION_OPEN_DOCUMENT_TREE` (Android 5.0+) grants access to a whole directory subtree; on Android 11+ it cannot be used on the internal-storage root and some other locations. [S] — [Android Developers: Open files using SAF](https://developer.android.com/guide/topics/providers/document-provider), [Access documents and other files from shared storage](https://developer.android.com/training/data-storage/shared/documents-files)
- Tree access is opt-in per provider and historically "few cloud storage providers seem to support ACTION_OPEN_DOCUMENT_TREE" (CommonsWare; old but never contradicted by anything found). A Dropbox forum thread asks Dropbox to support OPEN_DOCUMENT / CREATE_DOCUMENT / OPEN_DOCUMENT_TREE at all. [S] — [CommonsWare: Scoped Storage Stories: Trees](https://www.goodreads.com/author_blog_posts/19065823-scoped-storage-stories-trees?tab=author), [CommonsWare: SAF, Missing in Action](https://commonsware.com/blog/2017/12/27/storage-access-framework-missing-action.html), [Dropbox forum](https://www.dropboxforum.com/discussions/101000042/why-using-intent-action-open-document-does-not-list-the-dropbox/209654)
- Obsidian (the closest analogue: an app over a plain folder) documents that on Android the native OneDrive app "may not function well" (listed as limited functionality), Google Drive needs files set "Available offline", and the practical route is a third-party folder-sync app (Dropsync / DriveSync / OneSync / FolderSync) that mirrors a cloud folder into a **real local folder**, which the app then opens. [S] — [Obsidian Help: Sync your notes across devices](https://help.obsidian.md/sync-notes), [Obsidian forum: third-party syncing folders not visible on Android](https://forum.obsidian.md/t/third-party-syncing-folders-not-visible-in-file-picker-android/20978), [Obsidian forum: OneDrive sync on iOS and Android](https://forum.obsidian.md/t/feature-onedrive-sync-on-ios-and-android/20248/3), [Obsidian forum: SAF feature request](https://forum.obsidian.md/t/android-support-the-storage-access-framework-store-vault-in-google-drive-etc/23234)
- "Open with" from the OneDrive Android app into a third-party editor does not reliably write back: depending on the editor, edits may save back, or the user is prompted to save a local copy; users fall back to download → edit → re-upload. (Sources are mostly vendor how-tos — low authority.) [S] — [Microsoft Tech Community thread](https://techcommunity.microsoft.com/discussions/onedriveforbusiness/edit-a-text-file-saved-in-onedrive-on-android-options/2989704), [WPS how-to](https://www.wps.com/office-quick-solution/document-file-issues/how-to-edit-text-files-in-the-onedrive-android-app/)
- There is no iCloud Drive app or documents provider for Android (web access only). [BK] — [Apple: iCloud system requirements](https://support.apple.com/en-us/102465)
- iA Writer notes: "as of Jan 1, 2026 Dropbox no longer supports cloud storage access via the SDK used in Writer for Android", and iA Writer for Android is no longer sold — evidence that Android cloud integrations rot when not maintained. [S] — [iA Writer support: Cloud Storage](https://ia.net/writer/support/library/cloud-storage)

**iOS / iPadOS**
- `UIDocumentPickerViewController` can return a security-scoped URL for a **directory**; children enumerated from it are also accessible; a bookmark must be created after `startAccessingSecurityScopedResource`; always use file coordination for external documents. Picking a single file grants access only to that file, not to its parent folder (so sidecar files next to it are unreachable). [S] — [Apple: Providing access to directories](https://developer.apple.com/documentation/uikit/providing-access-to-directories), [Apple Developer Forums 797469](https://developer.apple.com/forums/thread/797469?answerId=854824022), [Apple Document Picker Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/DocumentPickerProgrammingGuide/CreatinganOutstandingUserExperience/CreatinganOutstandingUserExperience.html)
- Whether a third-party cloud can be picked **as a folder** depends on that provider's File Provider extension. A 2021 Apple forum report: when selecting folders "every 3rd party file provider is grayed out; only On My iPhone and iCloud Drive are available"; MacStories (iA Writer 5.2 review) says Dropbox, Google Drive and OneDrive "won't let you open folders from other apps such as iA Writer or Working Copy"; iA says a location can be added only if "the full folder can be accessed via the iOS Files API". Current (2026) status for each provider was **not** confirmed. [S] — [Apple Developer Forums 691738](https://developer.apple.com/forums/thread/691738), [MacStories: iA Writer 5.2](https://www.macstories.net/ios/ia-writer-5-2-better-typography-and-external-library-locations/), [iA Writer: Cloud Storage iOS](https://ia.net/writer/support/library/cloud-storage/cloud-storage-ios)
- iCloud Drive is the only cloud that is reliably folder-openable, background-synced by the OS, and conflict-aware (`NSFileVersion`) on iOS; Obsidian's own docs recommend iCloud only for Apple-to-Apple sync. [S] — [Obsidian Help: Sync your notes across devices](https://help.obsidian.md/sync-notes)

**Conflict behaviour of the providers (what the app will find on disk)**
- Dropbox: creates a second file whose name contains the editor/device name, the words "conflicted copy" and the date; separate "(Case Conflict)" suffix for case-only name clashes. [S] — [Dropbox Help: conflicted copy](https://help.dropbox.com/organize/conflicted-copy), [Dropbox Help: case conflict](https://help.dropbox.com/organize/case-conflict)
- OneDrive: keeps both and appends the **device name** to one copy (users also report "(1)"-style suffixes in some cases). [S] — [Digital Citizen: Cloud sync conflicts explained](https://www.digitalcitizen.life/cloud-sync-conflicts/) (third-party; exact rule not confirmed against Microsoft docs)
- Google Drive for desktop: reported to create a duplicate copy on conflict; exact naming not found in Google documentation. [S] — [Digital Citizen](https://www.digitalcitizen.life/cloud-sync-conflicts/)
- iCloud Drive: no extra file; versions held in `NSFileVersion` until an app (or Finder dialog) resolves. [S] — [Apple TN2336](https://developer.apple.com/library/content/technotes/tn2336/_index.html)
- Syncthing: loser renamed `<name>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`; conflict copies then propagate as normal files. Since 2.0, a delete can win a conflict, in which case the surviving edit is moved to a conflict copy. [S] — [Syncthing docs: Understanding Synchronization](https://docs.syncthing.net/users/syncing), [Syncthing 2.0 forum announcement](https://forum.syncthing.net/t/syncthing-2-0-august-2025/24758)

#### (b) Direct cloud API integration
- **Google Drive**: apps using restricted scopes need restricted-scope verification and, if restricted data is stored/transmitted on servers, an annual CASA security assessment; Google may push apps to narrower scopes. [S] — [Google: Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [Google Cloud Help: Security Assessment](https://support.google.com/cloud/answer/13465431)
- For a **personal** app the practical position is: while the OAuth consent screen is in "Testing", authorisations and refresh tokens expire after seven days; publishing to "In production" without submitting for verification removes the 7-day expiry but shows the unverified-app warning and applies a lifetime 100-user cap for sensitive/restricted scopes (the cap cannot be reset). A Workspace "Internal" app avoids both. No official "personal use" exemption from the cap was found on current pages. [S] — [Google Cloud Help: Manage App Audience](https://support.google.com/cloud/answer/15549945), [Google: OAuth production readiness overview](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview), [Google dev forum: personal-use app](https://discuss.google.dev/t/app-name-verification-failures-on-required-publishing-but-this-is-for-my-personal-use-only/354816)
- The `drive.file` scope (only files the app created or the user explicitly picked) is non-sensitive and avoids restricted-scope review, but it cannot see an arbitrary pre-existing folder tree; full `drive` is restricted. rclone documents the "own client ID, publish to production, don't verify" route for personal use. [BK] — [Google Drive API: choose scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [rclone: making your own client_id](https://rclone.org/drive/#making-your-own-client-id)
- **Microsoft Graph / OneDrive**: `driveItem: delta` gives an initial full enumeration then a `deltaLink` for incremental changes; delegated personal-account permissions listed for delta are Files.Read, Files.Read.All, Files.ReadWrite, Files.ReadWrite.All; consumer OneDrive omits some properties in delta results. Throttling numbers on the Graph page differ between versions surfaced by search (e.g. "130,000 requests per 10 seconds per app across all tenants" vs other figures) and "are subject to change" — irrelevant at one-user volume. [S] — [Microsoft Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0), [Microsoft Graph throttling limits](https://learn.microsoft.com/graph/throttling-limits), [OneDrive scan guidance](https://learn.microsoft.com/onedrive/developer/rest-api/concepts/scan-guidance)
- Microsoft app registration for personal Microsoft accounts is free and self-service in Entra; there is no Google-style security audit for a public-client app the owner consents to themselves. [BK] — [Microsoft identity platform: register an application](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app)
- **Dropbox**: a new app starts in development status; development apps can link up to 500 accounts; after 50 linked users there is a two-week window to obtain production approval; requests are not reviewed before 50 users — i.e. a one-user app never needs review. "App folder" vs "Full Dropbox" access types. [S] — [Dropbox developer guide](https://www.dropbox.com/developers/reference/developer-guide), [Dropbox forum: limit on development users](https://www.dropboxforum.com/discussions/101000014/does-a-dropbox-app-have-a-limit-on-development-users/846671)
- Dropbox change tracking: `list_folder` → `list_folder/continue` with a cursor, `get_latest_cursor`, and a long-poll endpoint; `content_hash` identifies bytes, `rev` identifies a revision; uploading with write mode `update(rev)` fails on mismatch unless `autorename=true`, in which case Dropbox makes the "conflicted copy" itself. A known quirk: longpoll may fire for changes outside the cursor's path. [S] — [Dropbox forum: handling local/remote rev differences](https://www.dropboxforum.com/discussions/101000042/handling-of-local-and-remote-rev-differences/397757), [Dropbox forum: WriteMode.update and conflicted copies](https://www.dropboxforum.com/t5/Dropbox-API-Support-Feedback/V2-API-s-DbxFiles-WriteMode-update-does-not-created-conflicted/td-p/133340), [Dropbox forum: longpoll workflow](https://www.dropboxforum.com/discussions/101000014/longpoll-workflow--flowchart--advice-how-to-do-it-right/341264)
- **WebDAV/Nextcloud and S3**: no universal delta feed; clients poll with ETags (WebDAV `PROPFIND`, S3 `ListObjectsV2`), so cost scales with tree size, and S3 has no rename (copy+delete). [BK] — [Nextcloud developer manual: WebDAV](https://docs.nextcloud.com/server/latest/developer_manual/client_apis/WebDAV/basic.html), [rclone: S3](https://rclone.org/s3/)

#### (c) Peer-to-peer / self-hosted file sync
- **Syncthing core**: 2.0 released August 2025 (LevelDB → SQLite database, three connections by default between v2 devices, rolling-hash shifted-data detection removed, deleted items forgotten after six months, deletes can win conflicts); 2.1.x followed. [S] — [Syncthing 2.0 (August 2025)](https://forum.syncthing.net/t/syncthing-2-0-august-2025/24758), [Neowin](https://www.neowin.net/news/syncthing-20-released-with-major-changes-switching-from-leveldb-to-sqlite/)
- **Syncthing on Android**: the official app was discontinued (announced Oct 2024, final release Dec 2024). [BK] — [Syncthing forum: Discontinuing syncthing-android](https://forum.syncthing.net/t/discontinuing-syncthing-android/23002)
- **Syncthing-Fork** then had its own upheaval: original maintainer Catfriend1 disappeared in late 2025 and the GitHub account/repo vanished; development moved to `researchxxl/syncthing-android` with `nel0x` doing Play Store releases; community raised trust issues (reduced communication, removal of SHA256/GPG release-verification tooling; an F-Droid issue titled "potential security breach in syncthing-fork"). A BasicSync note dated 2026-02-13 says the fork "appears to be actively maintained by new maintainers now"; F-Droid lists version 2.1.2.0 added 2026-07-10. Some users run the plain Syncthing binary under Termux instead; BasicSync (chenxiaolong) is an alternative minimal wrapper. [S] — [Syncthing forum thread](https://forum.syncthing.net/t/does-anyone-know-why-syncthing-fork-is-no-longer-available-on-github/25661), [Privacy Guides discussion](https://discuss.privacyguides.net/t/syncthing-fork-repo-with-new-repo-and-maintainers-anyone-have-a-take-on-this/33130), [F-Droid data issue 3712](https://gitlab.com/fdroid/fdroiddata/-/issues/3712), [researchxxl/syncthing-android](https://github.com/researchxxl/syncthing-android), [BasicSync issue 1](https://github.com/chenxiaolong/BasicSync/issues/1), [F-Droid listing](https://f-droid.org/packages/com.github.catfriend1.syncthingfork/)
- **Syncthing on iOS**: Möbius Sync (third-party, closed source) is the usual client. Its FAQ says no iOS app can run continuously in background; it connects only while open, briefly afterwards, and when iOS grants a background run. Users report background runs "typically every 5–15 min" but sometimes up to 24 h to start, and desktop peers showing the phone as disconnected; an always-on peer is recommended. Free tier limited to 20 MB; one-time purchase for unlimited. [S] — [Möbius Sync FAQ](https://mobiussync.com/faq), [Obsidian forum: Syncthing + Möbius Sync](https://forum.obsidian.md/t/sync-mac-pc-and-ios-using-syncthing-mobius-sync/72022), [Syncthing forum: Syncthing on iOS/iPadOS](https://forum.syncthing.net/t/syncthing-on-ios-ipados/24610)
- **rclone bisync**: still documented as beta / "advanced command, use with care" in the versions surfaced; conflict flags `--conflict-resolve`, `--conflict-loser`, `--conflict-suffix`; a 2026 user report (rclone v1.74.0) of the winner not being copied to the loser side with `--conflict-resolve newer --conflict-loser pathname`. [S] — [rclone bisync docs](https://rclone.org/bisync/), [rclone forum 53768](https://forum.rclone.org/t/bisync-does-not-copy-the-winner-file-to-the-loser-site/53768)
- **Nextcloud**: needs a server (self-hosted or rented); official clients exist for all four platforms, with an Android documents provider and an iOS File Provider extension. [BK] — [Nextcloud clients](https://nextcloud.com/install/#install-clients)
- **Iroh** (Rust p2p transport, "dial keys not IPs", QUIC with relay fallback): 1.0 released June 2026 asserting wire-protocol and API stability, adding QUIC multipath; 1.0.3 on docs.rs at time of search. This is a transport to build on, not a file-sync product. [S] — [Iroh 1.0 announcement](https://iroh.computer/blog/v1), [docs.rs iroh](https://docs.rs/crate/iroh/latest), [AlternativeTo news, June 2026](https://alternativeto.net/news/2026/6/iroh-1-0-launches-with-stable-key-based-addressing-and-broad-language-support/)

#### (d) App-owned sync service with E2EE (how others do it)
- **Obsidian Sync**: E2EE by default; password is unrecoverable; local vault is not encrypted. Default conflict mode "Automatically merge"; since Obsidian 1.9.7 a per-device option to "create conflict file" instead. [S] — [Obsidian Help: Sync security](https://obsidian.md/help/sync/security), [Obsidian Help: Sync troubleshooting](https://obsidian.md/help/sync/troubleshoot)
- Obsidian Sync merge rules: Markdown merged with Google's diff-match-patch; JSON settings merged key-wise (local keys applied over remote); all other file types "last modified wins". [BK; the diff-match-patch part was also asserted in a forum post surfaced by search] — [Obsidian Help: Sync troubleshooting](https://obsidian.md/help/sync/troubleshoot), [Obsidian forum: Robust Sync Conflict Resolution](https://forum.obsidian.md/t/robust-sync-conflict-resolution/93544)
- **Self-hosted LiveSync** (community plugin): CouchDB or S3-compatible object storage (MinIO/S3/R2) backend; CouchDB needs non-default configuration and HTTPS for mobile. [S] — [vrtmrz/obsidian-livesync](https://github.com/vrtmrz/obsidian-livesync)
- **Notion offline**: pages marked available-offline are migrated to a CRDT data model; a persistent local SQLite store tracks offline pages and why they are offline; the server pushes update notices and clients re-fetch only stale pages. [S] — [Notion blog: How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)
- **Logseq DB**: DB version in beta, RTC sync and new mobile app in alpha per the README; a 2026-07-13 update says DB beta and RTC sync are available to active backers; described as a custom CRDT-inspired protocol with per-graph E2EE and keys in platform keystores; changelog mentions custom sync-server URLs; two-way Markdown mirror still in development (May 2026). Self-hosting status is contradictory across sources. [S] — [Logseq GitHub](https://github.com/logseq/logseq/), [What's new with Logseq DB, 2026-05-16](https://discuss.logseq.com/t/whats-new-with-logseq-db-may-16th-2026/35020), [Logseq DB changelog](https://discuss.logseq.com/t/logseq-db-changelog/30013/37)
- **Anytype / any-sync**: open protocol; objects are encrypted CRDT change-DAGs; sync nodes are self-hostable; devices can sync peer-to-peer on a LAN. [BK] — [anyproto/any-sync](https://github.com/anyproto/any-sync)
- **Standard Notes**: E2EE notes with a self-hostable sync server. **Bear**: Apple-only, CloudKit private database. **iA Writer**: no sync service at all — plain files in iCloud/Dropbox/Google Drive/OneDrive "library locations". [BK for Standard Notes/Bear; S for iA] — [Standard Notes self-hosting](https://standardnotes.com/help/self-hosting/getting-started), [Bear FAQ: sync](https://bear.app/faq/sync-troubleshooting/), [iA Writer: Cloud Storage](https://ia.net/writer/support/library/cloud-storage)
- Hosting cost floor: Cloudflare R2 free tier is 10 GB-month storage, 1,000,000 Class A and 10,000,000 Class B operations per month, with free egress (Standard class only). [S] — [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- PocketBase (single Go binary + SQLite) was still pre-1.0 in the sources surfaced (0.2x line); 1.0 status unconfirmed. [S] — [PocketBase releases](https://github.com/pocketbase/pocketbase/releases)

#### (e) Local-first sync engines and CRDTs
- **Automerge 3.0** (2025): re-implemented to use its compressed columnar format in memory; official example: Moby Dick pasted into a document used ~700 MB in Automerge 2 and ~1.3 MB in Automerge 3; Ink & Switch describes "memory savings of 100x in some cases" and much faster load. [S] — [Automerge 3.0 blog](https://automerge.org/blog/automerge-3/), [Ink & Switch dispatch 011](https://inkandswitch.com/newsletter/dispatch-011)
- **Yjs** remains the default choice for collaborative text editors (largest ecosystem, editor bindings); **Loro** (1.0 out — sources disagree whether 2024 or 2025) benchmarks fastest and adds a movable-tree CRDT, with the smallest ecosystem; benchmark fairness is disputed (Yjs GC vs full-history retention). Comparison sources are low-authority blogs. [S] — [pkgpulse comparison](https://www.pkgpulse.com/guides/yjs-vs-automerge-vs-loro-crdt-libraries-2026), [Yjs forum: Yjs vs Loro](https://discuss.yjs.dev/t/yjs-vs-loro-new-crdt-lib/2567/4), [Loro repo](https://github.com/loro-dev/loro)
- **Zero** reached 1.0 (InfoQ, June 2026) and **PowerSync** has a "v1.0 stable release" post; **ElectricSQL** = Postgres read-path sync; **PowerSync** = Postgres/Mongo/MySQL → client SQLite; **LiveStore** = client-centric event-sourced SQLite; **Jazz** = local-first database with sync and permissions. All of these assume a server-side database or hosted sync service. [S, from result titles/summaries only] — [InfoQ: Zero version 1](https://infoq.com/news/2026/06/zero-version-1), [PowerSync v1.0](https://powersync.com/blog/powersync-v1-0-stable-release), [Electric: alternatives](https://electric-sql.com/docs/reference/alternatives)
- **Ditto**: commercial mesh-sync SDK (Bluetooth/LAN/P2P Wi-Fi) aimed at enterprise fleets. [BK] — [Ditto docs](https://docs.ditto.live/)

### Inferences
- A solo-developer ranking by *cost to build and keep working* (lowest first): (a) synced folder on desktop → (c) "user runs Syncthing/FolderSync/Möbius" on mobile → (b) one direct API client (OneDrive Graph or Dropbox are the least bureaucratic; Google full-Drive scope is the most) → (d) own E2EE blob service on R2-class storage → (e) CRDT engine for documents. Each step up buys smoother mobile behaviour at a real maintenance cost.
- Provider choice by platform coverage for *this* user: **OneDrive** is strongest on Windows and adequate on Mac, weak as a folder on Android/iOS; **iCloud Drive** is best on Apple devices, risky on Windows, absent on Android; **Dropbox** is the most app-friendly desktop folder and has the easiest API; **Google Drive** is fine on desktop (prefer mirror mode for an editor) but has the heaviest OAuth burden for whole-tree API access. No single provider gives a first-class third-party *folder* on all four platforms.
- CRDT libraries suit the **text** formats and structured app state; they do nothing for opaque .docx/.xlsx/.pptx/.pdf bytes (a CRDT can at best hold "which blob version is current"). For one user who is rarely on two devices in the same minute, whole-file versioning plus three-way text merge covers nearly all real conflicts; a CRDT is overkill for files and optional for state.
- Postgres-centred engines (Electric, PowerSync, Zero) are the wrong shape: they require a server database, which contradicts "no server, no recurring cost".
- Embedding a sync engine (libsyncthing via gomobile, or Iroh + custom protocol) makes the developer responsible for background execution, NAT traversal and data-loss bugs on four OSes; "tell the user to run one" costs nothing but gives a worse mobile experience. Iroh 1.0's stability promise makes a *later* embedded LAN/P2P sync plausible, not an early one.

## 2. Conflict handling per file type

### Takeaway
Text-like files can be merged automatically if the app keeps a **common ancestor** (last-synced base) per file; office and PDF binaries cannot be merged by a third-party app and should follow "never lose either version: keep both, pick a winner deterministically, show a banner". Real co-authoring for Word/Excel is a server protocol tied to OneDrive/SharePoint and is out of reach.

### Cited Findings
- Obsidian Sync's shipped policy is a ready-made precedent: Markdown → automatic diff-match-patch merge (docs admit it can occasionally duplicate text); JSON config → key-wise merge; everything else → last-modified-wins; optional per-device "create conflict file" mode since 1.9.7; conflict resolution setting is per device. [S + BK as in §1(d)] — [Obsidian Help: Sync troubleshooting](https://obsidian.md/help/sync/troubleshoot), [Obsidian Help: Sync settings (mirror)](https://www.mintlify.com/obsidianmd/obsidian-help/sync/settings)
- Folder-sync products never merge: Dropbox makes a "conflicted copy", OneDrive a device-name-suffixed copy, Syncthing a `.sync-conflict-…` copy, iCloud holds `NSFileVersion` conflict versions. [S] — sources as listed in §1(a)
- Syncthing conflict copies are themselves synced as ordinary files, and users report conflict "storms" for files written frequently from one machine. [S] — [Syncthing docs](https://docs.syncthing.net/users/syncing), [Syncthing forum: 4 sync-conflicts from one PC](https://forum.syncthing.net/t/just-working-on-one-document-one-pc-get-4-sync-conflicts/12688)
- Cryptomator (encrypted files inside a cloud folder) detects provider conflict suffixes on the encrypted name and re-attaches them to the decrypted name — showing that conflict-copy detection by filename pattern is workable but fiddly. [S] — [Cryptomator docs: Synchronization Conflicts](https://docs.cryptomator.org/desktop/sync-conflicts/)
- Office co-authoring works only for modern formats stored on OneDrive/SharePoint; when Office cannot negotiate a co-authoring lock it falls back to an exclusive lock; policies exist to disable automerge/co-authoring. [S] — [Microsoft Support: Troubleshoot co-authoring in Office](https://support.microsoft.com/en-us/office/troubleshoot-co-authoring-in-office), [Microsoft Tech Community thread](https://techcommunity.microsoft.com/discussions/sharepoint_general/cannot-release-lock-on-sharepoint-online-file/59694/replies/262377)
- Co-authoring is implemented by Office clients speaking MS-FSSHTTP (file sync over HTTP, "Cobalt") to SharePoint/OneDrive, or by WOPI hosts embedding Office for the web; it is not a property of the .docx file and there is no supported way for a third-party desktop editor to join a session. [BK] — [Microsoft Open Specifications: MS-FSSHTTP](https://learn.microsoft.com/en-us/openspecs/sharepoint_protocols/ms-fsshttp/05fa7efd-48ed-48d5-8d85-77995e17cc81), [Microsoft: WOPI/Cloud Storage Partner Program](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/online/)
- Lock hints in the wild: Word/Excel write an owner file `~$name.docx` next to the document; LibreOffice writes `.~lock.name.docx#`; Dropbox deliberately does not sync such temp files, so they are not a reliable cross-device lock over Dropbox. [BK] — [Dropbox Help: files that don't sync](https://help.dropbox.com/sync/files-not-syncing)
- Dropbox API offers server-side optimistic concurrency (`update(rev)`), the cleanest primitive for "don't overwrite what I haven't seen". [S] — [Dropbox forum](https://www.dropboxforum.com/t5/Dropbox-API-Support-Feedback/V2-API-s-DbxFiles-WriteMode-update-does-not-created-conflicted/td-p/133340)
- Git-based note apps expose raw merge conflicts; Obsidian Git on mobile has no rebase strategy and limited repo size. [S] — [Obsidian Git](https://github.com/vinzent03/obsidian-git)

### Inferences
Proposed per-file-type policy (design recommendation, not a sourced fact):

| Type | Detection | Automatic action | What the user sees |
|---|---|---|---|
| .md, .txt, source code | content hash differs from stored base on both sides, or a provider conflict-copy appears | three-way merge (diff3 or diff-match-patch) against the stored base; if hunks overlap, keep both files | non-overlapping: silent merge + undoable "merged changes from <device>" toast; overlapping: side-by-side merge view; never write conflict markers into the file silently |
| .csv | same | attempt row-keyed three-way merge only when a header and stable row order/key exist; otherwise treat as text merge; on overlap keep both | diff view by row; "keep mine / keep theirs / keep both" |
| .json app state | same | key-wise merge (as Obsidian does) or avoid shared files entirely (per-device files) | nothing |
| .docx / .xlsx / .pptx | same | **no merge**. Deterministic winner (newest mtime, tie → device id) stays at the path; loser saved as a named sibling or into version history | banner on open: "Edited on <device> at <time> while you had changes — compare / keep both / restore other"; optional read-only side-by-side |
| .pdf | same | if only annotations differ and annotations are held in a sidecar, merge the annotation sets by annotation id; if page content differs, treat as binary | usually nothing; otherwise as office files |

- Three-way merge needs a base. The cheapest way is a per-device **shadow copy or hash+snapshot of the last synced version** of each text file the app has opened (it doubles as local version history). Without a base, only two-way diff with user choice is safe.
- The app should **adopt** provider conflict copies rather than fight them: recognise the four naming patterns (Dropbox "conflicted copy", OneDrive device-name suffix, Syncthing `.sync-conflict-`, "(1)" duplicates) plus iOS/macOS `NSFileVersion` conflicts, group them with the original in the UI as "conflicting version", offer merge/keep/delete, and clean up after resolution.
- "Lock hints" are worth doing only as soft presence: a small `open-on-<device>` record with a heartbeat in the app's synced state lets device B warn "this file is open on your PC (last save 3 min ago)". It must be advisory and expire, because sync latency makes hard locks unsafe.
- Prevention beats resolution for one user: flush saves promptly on app background/quit, show sync-pending state, and reload-on-external-change when the buffer is clean. Most single-user conflicts come from an unsynced device being opened later.
- Atomic save (write temp file → rename over original) is safest for data integrity but makes some sync clients see delete+create; test per provider and prefer in-place replace APIs (`ReplaceFile` on Windows, `NSFileCoordinator`/`replaceItemAt` on Apple, SAF `openOutputStream("wt")` on Android).

### Gaps
- No primary source was found describing how the OneDrive sync client treats third-party writes to Office files it also co-authors (the "Use Office applications to sync Office files" setting and its interplay with non-Microsoft editors). Needs a spike.
- No evidence was gathered on robust three-way merge for CSV; treat as experimental.
- Whether `NSFileVersion` conflict versions are exposed for third-party File Provider clouds (not iCloud) was not established.

## 3. What to sync besides files, and how

### Takeaway
Put shareable app state in a hidden app folder inside the synced root so it rides the same transport as the documents, but design it so two devices never write the same file: one file (or append-only log) per device, small immutable records, and anything derivable (search index, backlink index, thumbnails) rebuilt locally and never synced.

### Cited Findings
- Obsidian keeps configuration in `.obsidian/` inside the vault; real-world cloud-folder sync of that folder produced "over 2,000 duplicates of the workspace file" under iCloud on Windows — the canonical example of a frequently rewritten session file causing a conflict storm. [S] — [Obsidian forum](https://forum.obsidian.md/t/over-2-000-duplicates-of-the-workspace-file-under-the-obsidian-folder/29965)
- Obsidian mitigations: separate `workspace.json` / `workspace-mobile.json`, an "override config folder" setting so a device can use a different config directory, and Sync toggles for which settings categories to sync. [BK] — [Obsidian Help: Configuration folder](https://help.obsidian.md/configuration-folder), [Obsidian Help: Sync settings](https://obsidian.md/help/sync/settings)
- Obsidian Sync merges JSON settings key-wise rather than whole-file. [BK] — [Obsidian Help: Sync troubleshooting](https://obsidian.md/help/sync/troubleshoot)
- KOReader stores reading position and annotations in a per-book sidecar (`.sdr`) next to the book or in a central folder; users syncing whole sidecars hit conflicts on layout-dependent fields (page numbers differ per device), and a developer advised syncing only the annotations file, later separated from layout settings (2025). [S] — [MobileRead thread](https://www.mobileread.com/forums/showthread.php?p=4474859), [koreader-calibre-plugin README](https://github.com/harmtemolder/koreader-calibre-plugin/blob/e71f567eb18ebd32cabf95832104a6c1e54751cd/README.md)
- Zotero keeps PDF annotations in its database rather than in the PDF, exporting them into the file only on request — the mainstream precedent for "sidecar first, embed on export". [BK] — [Zotero docs: PDF reader](https://www.zotero.org/support/pdf_reader)
- On iOS, picking a single file gives no access to its parent folder, so sidecars next to a document are unreachable unless the user granted the folder. [S] — [Apple Developer Forums 797469](https://developer.apple.com/forums/thread/797469?answerId=854824022)
- Syncthing forgets deleted items after six months (2.0) and can resurrect/demote files via conflict copies — relevant to tombstones in any app-level log. [S] — [Syncthing 2.0 announcement](https://forum.syncthing.net/t/syncthing-2-0-august-2025/24758)
- Syncthing has built-in file versioning modes (trash can, simple, staggered, external) that keep replaced/deleted versions on the receiving device. [BK] — [Syncthing docs: File Versioning](https://docs.syncthing.net/users/versioning.html)

### Inferences
Recommended state inventory (design recommendation):

| State | Scope | Where it lives | Sync mechanism / conflict rule |
|---|---|---|---|
| Settings, keybindings, themes | shared, with per-device overrides | `<root>/.app/settings.json` + `<root>/.app/devices/<id>/overrides.json` | key-wise merge with per-key timestamps; platform-specific keys (fonts, paths, shortcuts with Cmd/Ctrl) kept in the per-device file |
| Open tabs / session | per device, readable by others | `<root>/.app/devices/<id>/session.json` | only the owning device writes it; others read it to offer "Continue from PC: 4 tabs". Debounce writes (e.g. on tab change/idle), never per keystroke |
| Recent files | merged view | derive from each device's append-only `activity.log` | union, sorted by timestamp |
| Reading / cursor / scroll position | per file, last-writer-wins | entries in the per-device activity log keyed by file id; store logical anchors (page+offset for PDF, line/char or heading anchor for text, sheet+cell for xlsx, slide index) not pixel positions | newest timestamp wins; offer "jump to where you left off on <device>" rather than jumping automatically |
| PDF annotations | shared | sidecar `<root>/.app/annotations/<file-id>.json` with one record per annotation (uuid, modified time, tombstone) | set-merge by annotation id; "write into PDF" as explicit export/flatten or on user setting (embedded changes turn every highlight into a whole-file binary change and a conflict risk) |
| Version snapshots | per device by default | local app data (outside the synced root), content-addressed | not synced; rely on provider version history as the cross-device backstop; optionally sync a small manifest only |
| Full-text search index | per device | local app data | rebuild/incrementally update from file change events; never sync (large, platform-specific, churns) |
| Links/backlink index | per device (derived) | local app data | rebuild; but **link targets** stored in documents/sidecars should use relative paths plus a stable file id so renames on another device can be repaired |
| Stable file ids | shared | `<root>/.app/ids/…` or id embedded where the format allows (front-matter, custom doc property) | needed to keep annotations/positions/links attached across rename/move performed outside the app |
| Templates, snippets | shared | `<root>/.app/templates/` (ordinary files) | file-level rules from §2 |
| Fonts | not synced | — | record font names; show a "missing font on this device" notice; optionally allow user-supplied fonts in `.app/fonts/` (licence permitting) |
| Secrets (OAuth tokens, E2EE keys) | per device | OS keystore (DPAPI/Credential Manager, Keychain, Android Keystore) | never in the synced folder |
| Quick-capture inbox | shared | `<root>/Inbox/<timestamp>-<device>.md` (one file per capture) | create-only files cannot conflict |

- Sync-loop avoidance rules: (1) one writer per file; (2) write only when content actually changes (compare hash before writing); (3) ignore file-watcher events caused by the app's own writes (track expected hashes); (4) debounce; (5) append-only logs compacted only by the owning device; (6) include a device id and monotonic counter in every record; (7) keep the `.app/` folder small in file count, because Android SAF and cloud APIs enumerate slowly.
- A dot-folder is hidden on macOS/Linux but not on Windows (set the Hidden attribute) and some providers/mobile pickers skip dot-folders; name and behaviour must be tested per provider. If the documents are scattered in several roots, an app-state location per root (or one designated "home" root) is needed.
- If app state is the only thing that needs smooth multi-device merging, this is the one place a small CRDT document (Automerge/Loro/Yjs file per device, merged on read) could be justified later — but per-device files with key-wise merge deliver the same result with no dependency.

### Gaps
- No source measured how each provider handles many tiny, frequently changing files in a hidden folder on mobile (upload batching, rate limits, battery). Spike needed.
- Embedding stable ids in .docx/.xlsx/.pptx custom properties vs external id maps: no source consulted; overlaps with the documents/office research notes.

## 4. Continuity features and platform mechanics

### Takeaway
Native hand-off APIs do not span this user's device mix: Apple Handoff works only Apple-to-Apple, and Windows Cross-Device Resume is Android-to-PC, gated behind Microsoft approval and unavailable for iOS apps. The portable way to get "continue where I left off" everywhere is to derive it from synced per-device session state plus deep links, with native Handoff added as a cheap extra on Apple devices.

### Cited Findings
- **Apple Handoff**: an `NSUserActivity` can be continued only by an app with the same developer Team ID that declares the activity type (types listed in Info.plist); devices must be signed in to the same Apple Account with Wi-Fi and Bluetooth on and be near each other (Apple's Mac help says within 10 m / 30 ft). [S] — [Apple: About Handoff](https://developer.apple.com/library/ios/documentation/UserExperience/Conceptual/Handoff/HandoffFundamentals/HandoffFundamentals.html), [Apple: Adopting Handoff](https://developer.apple.com/library/mac/documentation/UserExperience/Conceptual/Handoff/AdoptingHandoff/AdoptingHandoff.html), [Apple Platform Support: Continuity](https://support.apple.com/guide/platform-support/sup60beac13c/web), [Mac Help](https://support.apple.com/en-in/guide/mac-help/mchl732d3c0a)
- Handoff payloads are small (`userInfo`, optional `webpageURL`); document-based apps hand off the iCloud document URL, so the file itself must already be reachable on the receiving device via sync. [BK] — [Apple: NSUserActivity](https://developer.apple.com/documentation/foundation/nsuseractivity)
- Universal Clipboard is a system feature between Apple devices on the same account; apps get it for free via the general pasteboard. [BK] — [Apple Support: Universal Clipboard](https://support.apple.com/en-us/102430)
- **Windows Cross-Device Resume**: shows a taskbar "Resume" badge on the PC for an activity begun on an Android phone. Builds 26100.7701 / 26200.7701 (Release Preview, January 2026) expanded it beyond OneDrive files to Spotify, Microsoft 365 apps and Edge. Android apps integrate the **Continuity SDK** to send an AppContext through Link to Windows; the Resume API is a **Limited Access Feature** requiring Microsoft's approval; Microsoft's docs state iOS apps are not currently supported; a server-driven alternative using WNS raw notifications is also described. [S] — [Microsoft Learn: Cross Device Resume](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/cross-device-resume), [Microsoft Learn: overview](https://learn.microsoft.com/en-ie/windows/apps/develop/windows-integration/cross-device-resume-overview), [Microsoft Support: Cross-device Resume](https://support.microsoft.com/en-us/windows/apps/phonelink/cross-device-resume-feature), [Windows Central](https://www.windowscentral.com/software-apps/windows-11/windows-11-is-getting-its-own-version-of-the-macs-handoff-feature-resume-apps-across-android-and-pc), [Windows Latest, 2025-11-25](https://www.windowslatest.com/2025/11/25/microsoft-is-using-windows-11-taskbar-to-resume-your-android-activities)
- **Android Cross device SDK**: still described as a Developer Preview (announced 2022), "should not be used in production apps", Android phones/tablets only; not labelled deprecated in the pages surfaced. [S] — [Android Developers: Cross device SDK overview](https://developer.android.com/guide/topics/connectivity/cross-device-sdk/overview), [Android Developers Blog, 2022](https://android-developers.googleblog.com/2022/07/announcing-cross-device-SDK-Developer-Preview-for-Android.html)
- Android sharing primitives available to any app: `ACTION_SEND` share targets (receive text/files from other apps), Quick Share to nearby Android/Windows devices via the system share sheet. [BK] — [Android Developers: Receive simple data from other apps](https://developer.android.com/training/sharing/receive)
- Deep links: iOS/macOS Universal Links and Android App Links need a domain hosting an association file (`apple-app-site-association`, `assetlinks.json`); custom URL schemes (`myapp://open?...`) need no domain and work on all four platforms (Windows via protocol activation). [BK] — [Apple: Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains), [Android: App Links](https://developer.android.com/training/app-links), [Microsoft Learn: Handle URI activation](https://learn.microsoft.com/en-us/windows/apps/develop/launch/handle-uri-activation)

### Inferences
- Portable continuity design (works on all four, no servers): every device writes `devices/<id>/session.json` (open tabs + per-tab logical position + timestamp). On launch/foreground, each app reads the others' files and shows "Continue from <device> — <file>, page 12, 3 min ago". Latency equals file-sync latency, which is the weak point on mobile (see §5).
- Deep link grammar should address files by **stable id and root-relative path**, never absolute path: e.g. `app://open?root=<root-id>&id=<file-id>&path=Notes/a.md&pos=line:120`. The same string can back Handoff `userInfo`, QR codes, "copy link to this place", and inter-document links.
- QR hand-off (PC shows a QR; phone camera opens the deep link) needs no pairing, no proximity radios and no account, and works across ecosystems; it only transfers the *pointer*, so the file must already be synced or the phone must fetch it.
- "Send to my other device" and a shared clipboard can be built as files in the synced inbox/outbox (`.app/handoff/<target-device>/…`); near-instant delivery requires a push channel or both apps in the foreground — otherwise it is "appears when you next open the app".
- Phone quick-capture is the highest-value continuity feature for the effort: register as a share target on Android (`ACTION_SEND`) and a Share Extension on iOS, write one new file per capture into `Inbox/`. Create-only files never conflict.
- Native extras worth their cost: Handoff between Mac and iPhone/iPad (small code, large perceived polish; requires same Team ID and that the file be in a location both can open). Windows Resume is **not** worth pursuing for a personal app while it is a Limited Access Feature; the Android Cross device SDK is not production-ready.

### Gaps
- Could not read Microsoft's Cross Device Resume page directly; the approval process, AppContext limits (size, lifetime) and whether unpackaged/personal apps can be approved are unverified.
- No 2026 source on Google's cross-device roadmap beyond the preview SDK page; no source checked on Quick Share ↔ AirDrop interoperability.
- No source consulted on Phone Link capabilities for iPhone ↔ Windows hand-off.

## 5. Mobile realities

### Takeaway
Neither mobile OS allows a third-party app to sync continuously in the background; design for "sync on open, on save, and opportunistically", make every file state (not downloaded / downloading / stale / upload pending) visible, and keep large files on-demand.

### Cited Findings
- iOS: Apple DTS position is that you cannot run code at a guaranteed interval; background execution is strictly limited. iOS 26 added `BGContinuedProcessingTask` (a user-initiated task that starts in the foreground and may continue in background with system progress UI); developers report it expiring unpredictably, including when the screen locks during an upload, and heavy throttling. [S] — [Apple: BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask), [Apple Developer Forums 805554](https://developer.apple.com/forums/thread/805554), [796138](https://developer.apple.com/forums/thread/796138), [797538](https://developer.apple.com/forums/thread/797538?answerId=854825022)
- Field evidence from a sync app (Möbius Sync): runs only while open, shortly after, and when iOS chooses; users see intervals from minutes to "up to 24 hours". [S] — [Möbius Sync FAQ](https://mobiussync.com/faq), [Obsidian forum](https://forum.obsidian.md/t/sync-mac-pc-and-ios-using-syncthing-mobius-sync/72022)
- iOS background `URLSession` transfers are performed by the system out-of-process and continue after the app is suspended — the supported way to finish uploads/downloads. [BK] — [Apple: Downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)
- Android: WorkManager periodic work has a 15-minute minimum interval and may be deferred by battery optimisations such as Doze; constraints (unmetered network, charging, battery not low) are declarative. [S] — [Android Developers: PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest), [Define work requests](https://developer.android.com/guide/background/persistent/getting-started/define-work)
- OEM battery managers (Xiaomi, Huawei, Samsung, OnePlus, etc.) kill background work beyond stock Android rules; documented per vendor by the community. [BK] — [dontkillmyapp.com](https://dontkillmyapp.com/)
- Cloud apps on phones do not keep whole folders locally: Obsidian's Android guidance requires marking Google Drive files "Available offline" or using a folder-mirroring app. [S] — [Obsidian Help: Sync your notes across devices](https://help.obsidian.md/sync-notes)
- Google notes offline files in stream mode are inaccessible when the Drive client is not running — the desktop analogue of the same partial-state problem. [S] — [Google Drive Help](https://support.google.com/drive/answer/13401938?hl=en)

### Inferences
- Minimum mobile sync contract: (1) on foreground: pull state + changed-file list; (2) on save: upload immediately via a background-capable transfer; (3) on background: flush pending writes within the short grace period; (4) periodic opportunistic job (WorkManager / `BGAppRefreshTask`) as a bonus, never as a correctness requirement.
- File states the UI and code must model on every platform: *cloud-only placeholder*, *downloading*, *local & current*, *local & possibly stale (offline)*, *locally modified, upload pending*, *conflict*, *evicted under storage pressure*. Opening a placeholder must be an explicit async operation with progress and cancel.
- Indexers (search, backlinks, thumbnails) must skip non-materialised files on all platforms or they will download the whole cloud (see the Cygwin/OneDrive report in §1).
- Phones: default to on-demand download with a per-folder "keep offline" pin, a "Wi-Fi only for files over N MB" setting, and an LRU cache budget; text files are small enough to keep fully offline.
- If the Android path is "companion folder-sync app + real local folder", the app itself needs no background sync at all on Android — a strong simplicity argument for that stage.

### Gaps
- Exact time budgets for `BGAppRefreshTask` / `BGProcessingTask` were not confirmed from Apple documentation in this session (commonly cited figures were deliberately not reproduced).
- No source on how Android 15/16 foreground-service data-sync time limits affect long uploads.

## 6. Security and privacy for personal sync

### Takeaway
The realistic threat model for a personal tool is device loss, account compromise and accidental data loss — not a nation-state. Default to trusting the user's chosen provider (optionally hardened by the provider's own E2EE), keep secrets in OS keystores, protect version history from sync-propagated deletion, and offer client-side encryption only as an opt-in layer because it breaks interoperability with every other app.

### Cited Findings
- Obsidian Sync: E2EE on by default, encryption password not recoverable by the vendor, data encrypted before leaving the device, local vault not encrypted; a published guide exists for verifying the encryption. [S] — [Obsidian Help: Security and privacy](https://obsidian.md/help/sync/security)
- Logseq DB sync: per-graph E2EE with keys stored in platform keystores. [S] — [Logseq DB changelog](https://discuss.logseq.com/t/logseq-db-changelog/30013/37)
- Cryptomator: client-side per-file encryption designed for cloud folders; filenames encrypted with AES-SIV bound to the parent directory id; losing the directory file loses names of its children; conflict copies need special handling. [S] — [Cryptomator docs: Vault security](https://docs.cryptomator.org/security/vault/), [Cryptomator docs: sync conflicts](https://docs.cryptomator.org/desktop/sync-conflicts/)
- `age`: simple file-encryption format with X25519 recipients and scrypt passphrase mode, chunked ChaCha20-Poly1305 payload. `rclone crypt`: per-file NaCl secretbox encryption with optional filename/directory-name encryption over any remote. libsodium `secretstream` is the usual primitive for chunked authenticated file encryption. [BK] — [age spec](https://age-encryption.org/v1), [rclone crypt](https://rclone.org/crypt/), [libsodium secretstream](https://doc.libsodium.org/secret-key_cryptography/secretstream)
- OneDrive, Google Drive and Dropbox hold the keys to stored files (provider can read content and metadata); iCloud Drive is end-to-end encrypted only with Advanced Data Protection enabled. [BK] — [Apple: iCloud data security overview](https://support.apple.com/en-us/102651)
- Syncthing-Fork's 2025–26 maintainer change removed checksum/GPG release verification — a supply-chain consideration when recommending third-party sync tools. [S] — [Privacy Guides discussion](https://discuss.privacyguides.net/t/syncthing-fork-repo-with-new-repo-and-maintainers-anyone-have-a-take-on-this/33130), [F-Droid data issue 3712](https://gitlab.com/fdroid/fdroiddata/-/issues/3712)
- Google's restricted-scope regime exists precisely because a whole-Drive token is a high-value secret. [S] — [Google: Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)

### Inferences
- Encrypting the user's documents in place (so the cloud sees ciphertext) defeats the product premise of "ordinary files in ordinary folders" — Word, Files apps, web previews and provider search stop working. Recommended: **do not encrypt documents by default**; point privacy-sensitive users at provider E2EE (iCloud ADP) or a Cryptomator-style vault as a separate root type.
- App-state files are a different matter: they are only read by this app, so encrypting them (age/libsodium with a key derived from a passphrase or a random key transferred by QR) is cheap and hides activity metadata (recent files, reading history) from the provider. Per-device X25519 keys with QR pairing ("scan this on your new device") avoid passphrases; keep a printable recovery key.
- If stage-3 direct API or own blob store is built, use per-file random content keys wrapped by a root key (allows sharing/rotation later), chunked AEAD, and encrypted names only where interoperability is already lost.
- Version history is a safety feature and a privacy liability: snapshots may retain text the user deleted. Keep them local by default, with a retention policy and a "purge history for this file" command; never sync deletions of history automatically.
- Ransomware/sync-propagated corruption is the most plausible catastrophic event for a sync-everything setup: provider version history (and a periodic offline backup) is the mitigation; the app should not be the only holder of versions.
- OAuth refresh tokens, if direct APIs are used, belong in Keychain / Android Keystore / Windows Credential Manager with the narrowest scope that works (app-folder or `drive.file` where possible).

### Gaps
- No source consulted on current retention limits of provider version history (OneDrive, Dropbox, Google Drive, iCloud) — needed to decide how much the app can lean on them.
- Obsidian Sync's exact cipher/KDF parameters were not confirmed in this session.

## 7. Git as a sync mechanism

### Takeaway
Git is an excellent optional layer for text/code folders on desktop (history, three-way merge, free hosting) and usable on iOS through Working Copy, but it is a poor default sync for this product: binary office files bloat history and cannot merge, and phone-side Git inside an app is memory-limited and fiddly.

### Cited Findings
- Obsidian Git on mobile uses isomorphic-git (pure JavaScript) because plugins cannot call native Git on Android/iOS; documented limitations: limited repo size due to memory, no SSH auth, no rebase merge strategy, no submodules; users report crashes on clone/pull; the maintainer says "I would not recommend using this plugin on mobile, but try other syncing services". [S] — [Obsidian Git (GitHub)](https://github.com/vinzent03/obsidian-git), [Obsidian Git docs: Getting Started](https://publish.obsidian.md/git-doc/Getting+Started), [Discussion 526](https://github.com/Vinzent03/obsidian-git/discussions/526)
- A community plugin author attributes the mobile problems to isomorphic-git loading entire packfiles into memory during clone/pull. [S] — [Obsidian community plugin: native-git-bridge](https://community.obsidian.md/plugins/native-git-bridge)
- Working Copy (iOS/iPadOS) is a full Git client that exposes repositories through the Files app as a file provider, so other apps can open a repo folder in place — one of the few third-party providers that supports folder opening. [BK; folder-open context from S] — [Working Copy users guide](https://workingcopy.app/manual/), [MacStories](https://www.macstories.net/ios/ia-writer-5-2-better-typography-and-external-library-locations/)
- GitJournal is an open-source Git-backed Markdown notes app for Android/iOS that auto-commits and pushes. [BK] — [GitJournal](https://gitjournal.io/)

### Inferences
- Where Git fits: (1) desktop "this folder is a Git repo" awareness — show status, auto-commit snapshots as version history for text, pull/push on demand; (2) power users who already keep code/notes in Git; (3) iOS via Working Copy as the file provider (the app only needs correct folder-bookmark and file-coordination behaviour).
- Where it fails: .docx/.xlsx/.pptx/.pdf (every save is a new blob; merges impossible; Git LFS adds a server dependency), non-technical recovery from merge conflicts on a phone, credentials/SSH on mobile, and any expectation of automatic background sync.
- Git's object model is still a useful *design reference* for local version snapshots: content-addressed blobs + per-device ref logs give deduplicated history without adopting Git as transport.

### Gaps
- No 2026 source confirmed GitJournal's maintenance status or Working Copy's current feature set/pricing.
- No evaluation was made of embedding libgit2/gitoxide natively in the mobile apps (would avoid isomorphic-git's limits at the cost of native build complexity).

## 8. Bottom line: staged strategy, policies, state map, risks, spikes

### Takeaway
Stage the work so the app never owns a sync engine until it has to: **Stage 1 (Windows only)** be an exemplary citizen of any synced folder; **Stage 2 (Android)** read/write a real local folder kept in sync by a companion tool, plus an inbox share-target; **Stage 3 (Apple)** iCloud-Drive-or-any-File-Provider folder with Handoff; only if those prove too rough add **one** built-in direct-API connector for the provider the owner actually uses. Conflict policy and the `.app/` state layout from §2–§3 stay constant across stages.

### Cited Findings
- Desktop synced folders are dependable for Dropbox/OneDrive/Google Drive (mirror) but iCloud Drive on Windows is flagged as risky by Obsidian's documentation and many user reports. [S] — [Obsidian Help](https://help.obsidian.md/sync-notes), [Obsidian forum](https://forum.obsidian.md/t/icloud-on-windows-creates-duplicate-files/48358)
- On Android, the documented working pattern for a folder-based app is a local folder synced by a third-party tool, not the cloud vendor's own app. [S] — [Obsidian Help](https://help.obsidian.md/sync-notes), [Obsidian forum](https://forum.obsidian.md/t/feature-onedrive-sync-on-ios-and-android/20248/3)
- On iOS, iCloud Drive is the dependable in-place folder; other providers' folder support is doubtful/unverified. [S] — [Apple Developer Forums 691738](https://developer.apple.com/forums/thread/691738), [iA Writer: Cloud Storage iOS](https://ia.net/writer/support/library/cloud-storage/cloud-storage-ios)
- A one-user direct-API client avoids formal review on Dropbox (under 50 users) and on Google if published unverified (warning screen, 100-user cap) — whereas "Testing" mode breaks every 7 days. [S] — [Dropbox developer guide](https://www.dropbox.com/developers/reference/developer-guide), [Google Cloud Help: Manage App Audience](https://support.google.com/cloud/answer/15549945)
- Syncthing is healthy on desktop (2.x) but its Android client situation changed hands twice in 2024–26 and iOS is limited by background rules. [S] — [Syncthing 2.0](https://forum.syncthing.net/t/syncthing-2-0-august-2025/24758), [Syncthing forum](https://forum.syncthing.net/t/does-anyone-know-why-syncthing-fork-is-no-longer-available-on-github/25661), [Möbius Sync FAQ](https://mobiussync.com/faq)
- Cross-device resume APIs are ecosystem-locked (Handoff: Apple only, same Team ID; Windows Resume: Android → PC, Limited Access, no iOS). [S] — [Apple: About Handoff](https://developer.apple.com/library/ios/documentation/UserExperience/Conceptual/Handoff/HandoffFundamentals/HandoffFundamentals.html), [Microsoft Learn: Cross Device Resume](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/cross-device-resume)

### Inferences

**Recommended staged strategy**

- **Stage 0 — design now, even with one device:** stable device id; stable file ids; `.app/` layout with one-writer-per-file; per-file base snapshot for text; deep-link grammar; file-state model (placeholder/stale/pending/conflict). These are cheap now and expensive to retrofit.
- **Stage 1 — Windows only:** no sync code. Be placeholder-aware (check recall attributes before reading; never hydrate during indexing; explicit "download to open" with progress), save safely (test atomic-save behaviour under OneDrive and Dropbox), watch for external changes and reload clean buffers, recognise and adopt provider conflict copies, keep local version snapshots, ignore/skip Office lock files. Recommend OneDrive or Dropbox; document Google Drive "mirror" mode; warn against iCloud for Windows.
- **Stage 2 — add Android:** open a **real local folder** (All-files access or SAF tree on local storage) and document supported companions: Syncthing-Fork (or successor) for PC↔phone with no cloud, or a FolderSync/Autosync-class app for OneDrive/Drive/Dropbox. Add: share-target → `Inbox/`, session/"continue from PC" via `.app/devices/*`, QR hand-off from PC, on-demand handling for large files if the companion supports it. Spike SAF tree access to cloud providers but do not depend on it.
- **Stage 3 — add Mac, iPhone, iPad:** macOS = same as Windows via `~/Library/CloudStorage/` or iCloud Drive, with `NSFileCoordinator`/`NSFilePresenter` and dataless-file awareness. iOS = folder picker with persisted bookmark; iCloud Drive as the recommended location for an Apple-heavy workflow, Working Copy or Möbius Sync folders as alternatives; `NSFileVersion` conflict resolution UI; Handoff via `NSUserActivity` between Apple devices; Share Extension → `Inbox/`.
- **The cross-ecosystem problem:** the owner has Windows + Android + Apple. iCloud covers Apple well and Windows badly and Android not at all; OneDrive/Dropbox/Google cover desktops well and phones only through their own apps. Expect to end up needing **Stage 4** for at least the phones.
- **Stage 4 — only if stages 2–3 are too rough:** one built-in connector (Dropbox API or Microsoft Graph first; Google Drive last because of scope friction) that syncs a chosen cloud folder into the app's own local storage on mobile, using delta/cursor APIs, rev-conditional uploads, background transfer APIs, and the same conflict policy. This is the first point where the developer owns sync correctness; budget for it as a major feature, with a property-based sync test harness. Abstract it behind a small "remote store" interface (list-changes, get, put-if-match, delete) so a WebDAV/S3 backend or own E2EE blob store can be added without redesign.
- **Not recommended for this user:** own hosted sync service, Postgres-based sync engines, CRDT-per-document storage, real-time co-editing.

**Per-file-type conflict policy (summary of §2):** text/Markdown/code → automatic three-way merge against stored base, side-by-side UI on overlap; CSV → text merge (row-aware only when safe), else keep both; JSON app state → per-device files / key-wise merge; office binaries and PDFs → keep both, deterministic winner, banner + version history; PDF annotations → sidecar set-merge by annotation id.

**State to sync and where it lives:** see table in §3 (shared: settings, templates, annotations sidecars, file ids, inbox; per-device-but-synced: session, activity log, overrides; local-only: search index, backlink index, thumbnails, version snapshots, secrets).

**Top risks**
1. **Mobile folder access is the make-or-break unknown** — cloud providers may not expose writable folder trees to third-party apps on Android (SAF) or iOS (File Provider); mitigations cost either user friction (companion app) or a Stage-4 connector.
2. **Silent data loss from sync races**: app overwrites a file whose newer version had not finished downloading; or atomic-save temp files confuse the provider. Mitigate with hash-before-write checks, base snapshots and local version history.
3. **Conflict storms in app state** (the Obsidian `workspace.json` pattern). Mitigate with one-writer-per-file and debounced writes.
4. **Placeholder hydration storms** from indexers/thumbnailers on on-demand folders (bandwidth, disk, battery).
5. **Dependence on third-party sync tools with shaky stewardship** (Syncthing-Fork maintainer turnover and verification-tooling removal; Möbius Sync is closed source; vendor SDK deprecations such as Dropbox's Android SDK change noted by iA).
6. **Platform churn and gating**: OAuth policy changes (Google), Limited Access Features (Windows Resume), iOS background rules; each built-in integration is a permanent maintenance liability for a solo developer.
7. **Binary-file conflicts are unresolvable** by design; user trust depends on never losing a version and explaining clearly what happened.
8. **Identity drift**: files renamed/moved outside the app break annotation/position/link attachment unless stable ids exist.

**Spike experiments (smallest tests that retire the biggest unknowns)**
1. *Android SAF matrix*: tiny test app calling `ACTION_OPEN_DOCUMENT_TREE` against Google Drive, OneDrive, Dropbox, Nextcloud, Proton Drive; record tree support, persisted permission, write-back, latency, offline behaviour.
2. *iOS folder-picker matrix*: same for iCloud Drive, OneDrive, Google Drive, Dropbox, Nextcloud, Working Copy, Möbius Sync; record folder selectability, bookmark persistence across reboot, coordinated write-back, conflict surfacing via `NSFileVersion`.
3. *Desktop save-strategy test*: write-in-place vs temp+rename vs `ReplaceFile` for a 20 MB .docx and a small .md under OneDrive, Dropbox, Google Drive (stream and mirror), iCloud for Windows; observe duplicate/conflict creation, version-history continuity, and upload latency.
4. *Two-device offline conflict drill*: edit the same .md, .csv, .docx and annotated .pdf offline on two devices for each provider; catalogue exactly what appears on disk (names, timestamps) to build the conflict-copy recogniser.
5. *Placeholder safety*: confirm the indexer and file tree never hydrate cloud-only files on Windows (recall attributes) and macOS (dataless files); measure with a 10 GB online-only folder.
6. *State-folder churn*: simulate a day of session/activity writes from three devices into `.app/` under each provider and Syncthing; count conflict copies and measure propagation delay.
7. *Three-way merge quality*: diff3 vs diff-match-patch on real note/code edits using stored bases; measure silent-wrong-merge rate.
8. *Continuity latency*: time from "close on PC" to "Continue from PC" appearing on Android and iPhone under each transport; decide whether a push channel is needed.
9. *Direct-API prototype (time-boxed)*: Dropbox or Graph delta-sync of one folder into app storage on Android with rev-conditional upload, to estimate Stage-4 cost honestly.
10. *Handoff*: `NSUserActivity` Mac ↔ iPhone for a file in iCloud Drive carrying a position anchor.
