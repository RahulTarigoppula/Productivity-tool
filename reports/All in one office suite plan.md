# Embed proven engines, own the file pipeline

A solo developer can reach near-dedicated-app breadth across .docx, .xlsx, .pptx and .pdf only by embedding an existing engine, and as of November 2026 the shortest credible path is the ONLYOFFICE editors running fully client-side through x2t compiled to WebAssembly, hosted in an Electron shell, with CodeMirror 6 for Markdown and plain text, a text-preserving CSV path, a permissive PDF engine (PDF.js or EmbedPDF), and headless LibreOffice plus Pandoc as conversion sidecars. The research does not support a promise of "no formatting corruption on save" from any engine: every editor that can edit Office files at full breadth converts the file into its own model and regenerates it, and no independent 2025–2026 round-trip benchmark exists for any candidate. The guarantee therefore has to come from the app's own file pipeline (keep the original, back it up before first save, write atomically, default to "save a copy" until a format passes a test corpus) rather than from engine choice. Truly lossless editing is architecturally possible only by patching the original package in place, and the open-source libraries built that way for .docx, .xlsx and .pptx are either young, limited in features, or commercial at the review-feature boundary. Licences split cleanly: the highest-fidelity engines (ONLYOFFICE, SuperDoc, MuPDF, PPTist) are AGPL-3.0, which costs nothing for a private, never-distributed tool but would bind the whole app if it were ever shared. Tabbed all-in-one office apps already exist (ONLYOFFICE Desktop Editors 10, Collabora Office), so the custom app earns its keep through the shell: Markdown, text and CSV as first-class peers, one command palette, one safe file pipeline, and a minimal look. Nothing in this report was tested hands-on; the first roadmap item should be a one-week spike and a personal document corpus.

## Every Office format stores less than it shows, so regeneration loses data

The three Office formats share one structural fact that drives every later decision: a .docx, .xlsx or .pptx is a ZIP package of interrelated XML parts wired by relationship files, defined by ECMA-376 / ISO/IEC 29500 ([ECMA-376](https://ecma-international.org/publications-and-standards/standards/ecma-376/)), and most of what the user sees is computed at render time rather than stored. An editor that reads the package into its own HTML or JSON model and writes a fresh file loses whatever that model cannot represent, silently. The format descriptions below come from the researchers' background knowledge of the specifications, because the spec hosts were unreachable during research; they are stable facts but should be spot-checked before being quoted as exact.

**Word documents** compute appearance through a style chain (document defaults, table style, paragraph style with `basedOn` inheritance, numbering level, character style, direct formatting, theme), store list numbers indirectly through `numPr` → `num` → `abstractNum` so the visible number is never in the file, hold fields such as page numbers and tables of contents as instructions with cached results, and write tracked changes as inline markup with author and date ([Microsoft: WordprocessingML structure](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document)). The evidence that conversion-based tools are lossy is direct. Pandoc's manual states it preserves "structural elements of a document, but not formatting details such as margin size" ([Pandoc manual](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)); Mammoth deliberately ignores fonts, sizes, colours and table borders ([mammoth.js](https://github.com/mwilliamson/mammoth.js)); docx-preview states that "Realtime page breaking is not implemented" ([docxjs](https://github.com/VolodymyrBaydalka/docxjs)). The features that force a paginating, OOXML-native engine rather than an HTML rich-text editor are sections, headers and footers, page-accurate fields, footnotes, floating images and columns. Exact layout equality with Word additionally needs the same fonts; EigenPal's editor warns that "Fallback measurement can change wrapping and pagination" ([EigenPal README](https://raw.githubusercontent.com/eigenpal/docx-editor/main/README.md)).

**Spreadsheets** lose data the same way. SheetJS, ExcelJS and xlsx-populate "all parse workbooks into proprietary object models, then re-serialize them as new files", dropping charts, pivot caches and macros that sit outside the model ([DEV Community](https://dev.to/pavkode/addressing-javascript-excel-library-flaws-a-new-approach-to-prevent-data-loss-and-ensure-2e5d)), and SheetJS carries a long-standing issue titled "Charts in file breaks roundtrip" ([SheetJS issue 111](https://git.sheetjs.com/sheetjs/sheetjs/issues/111)). Excel semantics add their own traps. Excel treats 1900 as a leap year for Lotus compatibility ([Microsoft KB 214326](https://support.microsoft.com/kb/214326)), and the 1900 and 1904 date systems differ by **1,462 days** ([Microsoft](https://learn.microsoft.com/en-US/office/troubleshoot/excel/1900-and-1904-date-system)). Newer functions are stored with an `_xlfn.` prefix, and a writer that omits it produces `#NAME?` in Excel ([libxlsxwriter](https://libxlsxwriter.github.io/working_with_formulas.html)). Dynamic arrays depend on a cell-metadata part that even openpyxl does not implement ([openpyxl issue 1898](https://foss.heptapod.net/openpyxl/openpyxl/-/issues/1898)), and LibreOffice destroys threaded-comment metadata when it re-saves an .xlsx ([LibreOffice bug 127105](https://lists.freedesktop.org/archives/libreoffice-bugs/2019-August/211141.html)).

**Presentations** push inheritance furthest: a placeholder on a slide usually has no position, size, font or bullet of its own and resolves through slide → layout → master → theme ([Microsoft: PresentationML structure](https://learn.microsoft.com/en-us/office/open-xml/presentation/structure-of-a-presentationml-document)). Text autofit scale values are computed by PowerPoint's layout engine and cached in the file, so any other editor must recompute them or leave them stale ([python-pptx autofit analysis](https://python-pptx.readthedocs.io/en/latest/dev/analysis/txt-autofit-text.html)). The most complete open-source browser renderer of 2026 still lists animations, transitions, exact text layout, EMF/WMF and OLE as unsupported and calls its chart layout "approximate" ([pptx-renderer](https://github.com/aiden0z/pptx-renderer)). The best single-maintainer web slide editor, PPTist, self-reports roughly **85% import and 95% export fidelity** and says "100% fidelity cannot be guaranteed" ([PPTist](https://github.com/pipipi-pikachu/PPTist)). Even Figma ships PowerPoint export that users report as broken on text alignment ([Figma forum](https://forum.figma.com/report-a-problem-6/figma-slides-export-to-pptx-text-align-property-set-to-middle-in-exported-files-41505)).

**PDF** inverts the problem. A PDF is a graph of numbered objects with a cross-reference table, and changes can be appended as an incremental update that leaves the original bytes untouched, which is why annotation, form filling and signing are safe by construction ([ISO 32000-1](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)). Page text, by contrast, is positioned glyph runs with subset fonts and no paragraph model; pdf-lib documents that it cannot edit page text outside form fields ([pdf-lib](https://github.com/Hopding/pdf-lib)), and Stirling-PDF's text editor needed server-provided fonts and font subsetting on save as late as v3.4.0 in November 2026 ([Stirling-PDF releases](https://github.com/Stirling-Tools/Stirling-PDF/releases)). Two rules follow: annotate, fill and sign through incremental saves, and treat redaction as a full rewrite, because an incremental save retains the "deleted" content in earlier revisions.

**Markdown, plain text and CSV** have no package to lose, so fidelity here means not reformatting. A tree-based Markdown editor re-serialises on every save, and remark-stringify states plainly that it "will do its best to serialize markdown to match the syntax tree, but there are several cases where that is impossible" ([remark-stringify](https://unifiedjs.com/explore/package/remark-stringify/)). An editor that keeps the text itself as the document saves it "byte-for-byte identical to a plain textarea" ([Atomic Editor](https://www.npmjs.com/package/@atomic-editor/editor)). For text and CSV the app's file layer has to preserve encoding, byte-order mark, line endings, trailing newline, delimiter and quoting style, because neither the editor nor the parser does; Papa Parse's `dynamicTyping` should stay off for identifiers with leading zeros ([Papa Parse parsing docs](https://tessl.io/registry/tessl/npm-papaparse/files/docs/parsing.md)).

The architectural lesson is the same in every Office format. Lossless save requires keeping the original package and patching only the parts that changed, passing everything else through byte-for-byte. Full-featured editing requires a complete model and layout engine. No open-source option delivers both today, so the plan has to pick breadth and buy safety separately.

## Feature expectations fall into three tiers per format

The tiering below is the researchers' synthesis of Word, Excel, PowerPoint, Google Workspace, ONLYOFFICE and Acrobat-class feature sets; no single authoritative source ranks these features, and the vendor help centres were not fetched. Its value for planning is the boundary it draws: a custom-built editor can reach the must-have tier, an embedded suite covers the expected tier, and the advanced tier should be scoped as "preserve on round trip and display" unless the embedded engine already provides it. Real-time collaboration is omitted throughout as irrelevant to a single-user tool, but tracked changes and comments are not, because they are stored in files that other people send.

| Format | Must-have | Expected | Advanced / professional |
|---|---|---|---|

| .xlsx / .csv | Multi-sheet workbook, formula bar, core functions, number formats, cell styling, merge, freeze panes, sort and filter, fill handle, undo, clipboard interop, basic charts, CSV and XLSX open/save | Conditional formatting, data validation, named ranges, tables with structured references, custom number formats, comments, print setup, XLOOKUP and dynamic arrays, LET | Pivot tables and charts, slicers, LAMBDA, what-if tools, macros, Power Query, external links, sparklines, threaded comments |

Open-source building blocks mark where each tier ends in practice. Univer's open-source Docs lists only rich text, paragraph formatting, lists, hyperlinks, comments and drawing integration ([Univer](https://github.com/dream-num/univer)), a fair picture of a "basic" word processor. PPTist's feature list (rich text, shapes, eight chart types, tables, video, LaTeX, presenter view, transitions and element animations) shows that one person can ship most of the first two presentation tiers when the document model is their own ([PPTist](https://github.com/pipipi-pikachu/PPTist)). ONLYOFFICE, a full-time team's product, was still adding slide-master UI, text animations and GIF playback across versions 9.0 to 9.4 ([ONLYOFFICE 9.1](https://onlyoffice.com/blog/2025/10/docs-9-1-released); [ONLYOFFICE 9.4](https://onlyoffice.com/blog/2026/05/onlyoffice-docs-9-4)) and only gained Ctrl+D fill-down in 10.0 ([ONLYOFFICE blog](https://www.onlyoffice.com/blog/2026/11/onlyoffice-10-features-you-asked-for)), which calibrates how long the advanced tier takes even with a team.

## Only two engine families edit real Office files at full breadth

The decision space for .docx, .xlsx and .pptx is effectively two engines, ONLYOFFICE and LibreOffice, plus a set of per-format components that are more hackable but narrower. Everything else found is a derivative of those two, proprietary, or stale.

### ONLYOFFICE runs with no server through x2t-WASM

ONLYOFFICE is the only open-source engine whose complete editor UI for all four heavy formats has been shown to run entirely client-side. Its editors (`sdkjs` and `web-apps`) do not edit OOXML directly; the `x2t` converter in `core` turns the file into an internal binary format and back ([ONLYOFFICE DesktopEditors](https://github.com/ONLYOFFICE/DesktopEditors)). CryptPad maintains x2t compiled to WebAssembly ([cryptpad/onlyoffice-x2t-wasm](https://github.com/cryptpad/onlyoffice-x2t-wasm)), and the community project **ranuts/document** (AGPL-3.0, about 2.0k stars) packages the stock editors with it as a static site whose "core document processing runs locally" ([ranuts/document](https://github.com/ranuts/document)). It offers full editing for .docx, .xlsx, .csv and .pptx, opens legacy and ODF formats and PDF, and exports any supported document to PDF.

Its embed API is almost exactly the surface a tabbed desktop shell needs. The parent posts `document:open-buffer` with an ArrayBuffer, `document:save` with an optional target extension, `document:set-readonly` and `document:get-state`; the iframe emits `document:ready`, `document:saved` with the file bytes, and `document:dirty-changed` when the dirty flag flips ([ranuts embed API](https://github.com/ranuts/document/blob/main/docs/embed-api.md)). Three limits are documented or evident. The `targetExt` list covers DOCX, XLSX, PPTX and CSV but not PDF, so programmatic PDF export needs a patch. The embed API documents no options for hiding chrome or theming. PDF support is described as "annotate, fill, and export" rather than the full PDF editor.

Upstream is active: Document Server **10.0.0 is dated 12 October 2026**, with a feature release roughly every two to three months through 2025–2026 ([DocumentServer releases](https://github.com/ONLYOFFICE/DocumentServer/releases)). The WASM route trails it; CryptPad's build instructions reference core tag v9.3.0.140, and ranuts does not state which version it bundles. The alternative of bundling the real Document Server as a local sidecar uses the official `DocsAPI` with a file URL and save callback ([ONLYOFFICE Docs API](https://api.onlyoffice.com/docs/docs-api/get-started/basic-concepts/)), at the cost of a heavier footprint and packaging work on Windows and macOS.

### LibreOffice offers more breadth but no embeddable widget

The LibreOffice family has the broadest feature and format coverage under MPL-2.0 ([LibreOffice licences](https://www.libreoffice.org/about-us/licenses)), and Collabora proved the "web UI over an in-process engine, no server" architecture with its new Collabora Office desktop app, first released in November 2025 ([Collabora press release](https://www.collaboraonline.com/blog/press-release-bringing-collabora-online-to-the-desktop/)) and updated as 26.04 in 2026 ([Collabora Office 26.04](https://www.collaboraonline.com/blog/collabora-office-26-04-release/)). No documented API was found for embedding that UI as a component in another app. The options are binding LibreOfficeKit natively and drawing all UI yourself ([LibreOfficeKit](https://docs.libreoffice.org/libreofficekit.html)), running the Linux-only `coolwsd` server with a local WOPI host ([Collabora Online SDK](https://sdk.collaboraonline.com/)), or ZetaOffice's WASM build, whose `zetajs` wrapper has 231 stars and no GitHub releases ([zetajs](https://github.com/allotropia/zetajs)) and whose UI is the classic LibreOffice toolkit rendered into a canvas ([FOSDEM 2025 slides](https://fosdem.org/2025/events/attachments/fosdem-2025-5169-lowa-in-need-of-a-vcl-plug/slides/236790/FOSDEM25_mjUvdiJ.pdf)). LibreOffice's strong role for this project is as a headless conversion sidecar via `soffice --headless --convert-to` ([LibreOffice start parameters](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)).

Which engine round-trips Office files better is not settled by evidence. The common assessment is that ONLYOFFICE, being OOXML-native, tracks Word and PowerPoint layout more closely while LibreOffice wins on breadth; the one comparative study found reports that both lose information on round trip to differing degrees, and its rigour is unverified ([comparative study](https://akrillick.github.io/web/archive/A%20Comparative%20Study%20of%20OOXML%20and%20ODF%20Implementations.pdf)).

### Univer is a spreadsheet toolkit, not an offline suite

Univer (Apache-2.0 core, about 31k stars) has the cleanest architecture and total UI control, but its repository states that Office file import and export, charts, pivot tables and collaboration are commercial, and that Slides is a "separately distributed commercial product" ([Univer](https://github.com/dream-num/univer)). The unlicensed tier caps import at 1 MB and export at 10,000 cells with a watermark ([Univer Pro licence docs](https://docs.univer.ai/guides/pro/license)). It fits only a spreadsheet-first design where the developer writes the XLSX layer.

The pattern is consistent. Components give a custom UI and, in principle, safer saves, but each either moves review features behind a commercial licence, is pre-1.0, or drops charts, pivots, animations and masters. Luckysheet is archived ([Luckysheet](https://github.com/dream-num/Luckysheet)), Handsontable is no longer open source ([Handsontable](https://github.com/handsontable/handsontable)), and Tiptap and CKEditor put DOCX conversion behind paid, service-backed features ([Tiptap DOCX docs](https://tiptap.dev/docs/conversion/import-export/docx); [CKEditor Import from Word](https://ckeditor.com/docs/ckeditor5/latest/features/import-word.html)). For a brief that asks for "as close to the full feature set as possible" across four heavy formats from one developer, components cannot match an embedded suite on breadth. They remain the right second engine to prototype for .docx specifically, where SuperDoc is the strongest embed-a-component candidate.

### Markdown, text and CSV get dedicated light engines

CodeMirror 6 (MIT; `@codemirror/view` 6.43.15) should serve both .md and .txt, with Markdown rendered through view-only decorations so saves never reformat the file ([npm: @codemirror/view](https://www.npmjs.com/package/@codemirror/view); [Atomic Editor](https://www.npmjs.com/package/@atomic-editor/editor)). Replit measured Monaco and related libraries at **51.17 MB** of bundle and noted CodeMirror's first-class mobile support ([Replit](https://replit.com/blog/codemirror)), and Sourcegraph migrated from Monaco to CodeMirror for similar reasons ([Sourcegraph](https://sourcegraph.com/blog/migrating-monaco-codemirror)). Milkdown (ProseMirror plus remark) gives the most Typora-like experience ([Milkdown](https://raw.githubusercontent.com/Milkdown/milkdown/main/README.md)) but canonicalises Markdown on save, so it suits only an opt-in mode. Live-preview decorations in CodeMirror are real custom work, and the small open-source packages that provide them are young. For CSV, Papa Parse 5.7.1 (MIT) handles delimiter detection, streaming and workers ([Papa Parse](https://www.npmjs.com/package/papaparse)); the design rule is to load every field as text, rewrite only edited cells, and write back the detected dialect. Whether CSV should open in the embedded spreadsheet engine or a dedicated grid is a product choice: the embedded engine gives formulas, the dedicated path gives fidelity.

### PDF has two permissive stacks and one AGPL powerhouse

**PDF.js** (Apache-2.0, pdfjs-dist 6.5.438 published 1 November 2026) releases roughly monthly and now ships highlight, free-text, ink, stamp and signature editors plus signature verification since v6.2 ([pdfjs-dist](https://registry.npmjs.org/pdfjs-dist/latest); [PDF.js releases](https://github.com/mozilla/pdf.js/releases)). Mozilla positions it as "designed for reading", supporting creation of only "a subset of the possible annotation types" ([PDF.js FAQ](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions)). **EmbedPDF** (Apache-2.0, PDFium compiled to WebAssembly) is the only permissive option covering viewing, annotations, form fill and build, redaction, page editing, and signing with validation in one engine, and Stirling-PDF adopted it for its viewer; its v3.0.0 shipped on 6 November 2026 with four minor versions in ten days and 229 open issues ([EmbedPDF](https://github.com/embedpdf/embed-pdf-viewer); [releases](https://github.com/embedpdf/embed-pdf-viewer/releases)). **MuPDF.js** 1.28.6 is the most capable single engine including redaction, under AGPL-3.0 or a commercial licence ([mupdf.js](https://github.com/ArtifexSoftware/mupdf.js)).

For page tools, the original pdf-lib has not been published since 2021 ([npm: pdf-lib](https://registry.npmjs.org/pdf-lib)); the maintained fork `@cantoo/pdf-lib` 2.11.1 adds encryption and incremental updates ([cantoo-scribe/pdf-lib](https://github.com/cantoo-scribe/pdf-lib)), and `@libpdf/core` 0.5.3 adds PAdES signing up to B-LTA while describing itself as beta ([LibPDF](https://github.com/LibPDF-js/core)). qpdf 12.4.2 covers repair, linearisation and decryption as a small sidecar ([qpdf releases](https://github.com/qpdf/qpdf/releases)). Tesseract.js 7.0.0 (Apache-2.0) provides in-app OCR ([npm](https://registry.npmjs.org/tesseract.js/latest)). True text editing of existing PDF content exists in open source only in ONLYOFFICE's PDF editor ([ONLYOFFICE 9.3](https://onlyoffice.com/blog/2026/02/onlyoffice-docs-9-3)) and Stirling-PDF, whose desktop editor directories fall outside its MIT grant ([Stirling-PDF LICENSE](https://raw.githubusercontent.com/Stirling-Tools/Stirling-PDF/main/LICENSE)). PDF to DOCX is lossy everywhere; pdf2docx says it "can't 100% convert the PDF layout" ([pdf2docx](https://pypi.org/project/pdf2docx/)). The plan should not promise it.

The conservative choice is PDF.js viewer components with their built-in editors for the reader and first annotation tier, with EmbedPDF prototyped in parallel and an engine-agnostic annotation model so the engine can be swapped once EmbedPDF v3 settles.

## Electron, one view per document, and a shell-owned file pipeline

### Electron removes the webview risk the editors would otherwise carry

The editors that matter are developed against Chromium, and Electron ships one known Chromium on every operating system; the latest stable seen was **Electron 45.3.3 with Chromium 156**, released 14 November 2026 ([Electron releases](https://releases.electronjs.org/)). Tauri v2 uses three different system webviews, and Tauri's own documentation warns that on Linux, WebGL and canvas content "can silently land on a slow path while the rest of the app looks fine" ([Tauri: Linux graphics issues](https://v2.tauri.app/develop/debug/linux-graphics/)). Tauri's multi-webview mode is still behind an `unstable` flag ([Tauri v2.12.0 notes](https://v2.tauri.app/release/tauri/v2.12.0/)), and it has no programmatic print-to-PDF, with feature requests open since 2022 ([Tauri issues](https://github.com/tauri-apps/tauri/issues?q=is%3Aissue+print+to+pdf)). A browser-only PWA is ruled out because `showOpenFilePicker()` is unsupported in Firefox and Safari ([caniuse](https://caniuse.com/mdn-api_window_showopenfilepicker)) and a page cannot spawn converters.

Tauri's headline advantage is size; benchmarks put small Tauri apps at tens of megabytes against hundreds for Electron ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)). That advantage largely disappears once the app bundles office editor assets or a LibreOffice install. The products closest to this project bundle a browser engine or own one: ONLYOFFICE Desktop hosts its editors in Chromium Embedded Framework ([ONLYOFFICE forum](https://community.onlyoffice.com/t/why-does-it-contain-a-web-browser/8250)), and Obsidian ships Electron several majors behind current ([codenote.net audit](https://codenote.net/en/posts/famous-electron-apps-2026-research/)). The cost of Electron is upkeep: only the latest three majors are supported, with a new major roughly every eight weeks ([endoflife.date](https://endoflife.date/electron)). No source measured ONLYOFFICE or Univer inside WKWebView or WebKitGTK, so the Tauri risk is inferred; a one-day spike would settle it.

### One WebContentsView per tab isolates crashes at the cost of overlays

`BrowserView` is deprecated and `WebContentsView` replaces it, attached with `win.contentView.addChildView(view)` ([Electron migration blog](https://electronjs.org/blog/migrate-to-webcontentsview)). Hosting each open document in its own view gives a separate renderer process, crash isolation and the ability to destroy and recreate views to hibernate background tabs. The main cost is that native views sit above the shell's DOM, so the command palette needs its own top-most view or the active editor must be hidden while it is open. Same-origin iframes are simpler and adequate for the light editors. Editor views should run sandboxed with context isolation, served from a custom protocol rather than `file://`, per Electron's security checklist ([Electron security](https://electronjs.org/docs/latest/tutorial/security)); document views need no network at all. Per-tab memory for an ONLYOFFICE-class editor was not found in any source and must be measured.

### A ten-method provider contract keeps engines replaceable

VS Code's custom-editor model is the proven template: a registry maps filename patterns to a provider, binary formats use a `CustomDocument`, and the provider implements save, save-as, revert and backup while the workbench owns tabs, dirty state and hot exit ([VS Code Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors)). Theia implements the same API, so the model works in a second independent shell ([Theia API](https://eclipse-theia.github.io/theia/docs/next/interfaces/plugin.CustomDocumentBackup.html)). For this app the contract reduces to open(bytes), getBytes(format), dirty-change events, a command list, command execution, optional text extraction for search, state capture for hibernation, theme, focus and dispose. Engines only ever see bytes over a message bridge; the shell owns file I/O, atomic writes, recovery, watching, recents, conversions and keybinding arbitration. This boundary matters more than any single engine choice, because the research cannot yet say which .docx engine will win a bake-off.

### The file pipeline is where "no corruption" is actually enforced

VS Code's hot-exit design is the best-documented reference: backups are written about one second after edits stop, kept outside the user's file, and deleted when superseded or saved ([CustomEditorProvider reference](https://vscode-api-cn.js.org/interfaces/vscode.CustomEditorProvider.html)). The pipeline that follows from the notes has five rules. Every save writes a temporary file in the same directory, syncs it, and renames it over the target. Office formats default to recovery snapshots rather than true auto-save, because each save through the ONLYOFFICE route is a full x2t conversion and a fidelity risk, while .md, .txt and .csv can auto-save. The app keeps a backup of the original before its first save of any file, plus a rolling set of snapshots as cheap version history. External changes are detected by watching the parent directory and comparing size, time and hash. And the app respects the lock files other suites write: LibreOffice's `.~lock.<name>#` plain-text record ([Ask LibreOffice](https://ask.libreoffice.org/t/lock-filename-odt/13437)) and Word's hidden `~$` owner file ([Microsoft Support](https://support.microsoft.com/en-us/topic/description-of-how-word-creates-temporary-files-66b112fb-d2c0-8f40-a0be-70a367cc4c85)). Macro-enabled files and digitally signed PDFs deserve explicit warnings, since saving either through an editing engine can drop the macro project or invalidate the signature.

### One registry feeds the palette; the shell reserves a few chords

`cmdk` is the headless palette primitive that shadcn/ui's Command component wraps, and 2026 tooling guides treat it as the default over the older kbar ([pkgpulse comparison](https://www.pkgpulse.com/guides/cmdk-vs-kbar-vs-mantine-spotlight-2026)). The design is a shell-owned command registry with three sources: shell commands, per-format commands published by the active editor session, and dynamic providers for files and content search. Embedded editors claim many chords, including Ctrl+K for "insert hyperlink", so the shell should reserve a short list (palette, save, close tab, switch tab, new, open), intercept them before the editor view sees them through Electron's input events ([Electron webContents](https://www.electronjs.org/docs/latest/api/web-contents)), and offer Ctrl/Cmd+Shift+P as an alias. SQLite FTS5 gives persistent ranked full-text search across documents ([SQLite FTS5](https://www.sqlite.org/fts5.html)). No source describes an existing app that unifies commands from several embedded third-party editors in one palette; this is novel integration work, and its depth depends on how much each engine exposes programmatically, which was not established for the ONLYOFFICE WASM route. A curated set of commands per engine is the realistic first target. For the shell UI itself, React with dockview (MIT core, with tabs, splits and popout groups) is the conservative stack ([dockview](https://dockview.dev/)), though a plain tab strip is enough to start.

### Conversion and export route by fidelity need

| From → to | Tool | Caveat |
|---|---|---|
| .docx / .xlsx / .pptx → .pdf | The editing engine's own export, or headless LibreOffice | LibreOffice headless is a 500 MB-plus dependency with reports of output differing from its GUI ([DEV comparison](https://dev.to/jakexkim/convert-docx-to-pdf-in-nodejs-every-option-compared-1oee)) |
| .md ↔ .docx, .docx → .md, .md → .html | Pandoc WASM | Official WASM build since Pandoc 3.9, February 2026 ([pandoc-announce](https://groups.google.com/g/pandoc-announce/c/znue-42hMeI)); structural, not layout, fidelity; GPL-2.0-or-later ([pandoc-wasm](https://www.npmjs.com/package/pandoc-wasm)) |
| .md / .txt / HTML → .pdf | Electron `webContents.printToPDF` with print CSS | Typst WASM for typeset output ([typst.ts](https://www.npmjs.com/package/@myriaddreamin/typst.ts)); Paged.js has had no release since 2023 ([npm](https://www.npmjs.com/package/pagedjs)) |
| .csv ↔ .xlsx | The spreadsheet engine | Encoding, delimiter and type coercion need explicit handling |
| Legacy .doc / .xls / .ppt, ODF | LibreOffice headless or x2t | LibreOffice 26.2 also added Markdown import and export ([heise](https://heise.de/-11165526)) |
| .pdf merge / split / rotate / repair | `@cantoo/pdf-lib` or `@libpdf/core`; qpdf | Write to a new file or keep a backup for full rewrites |
| .pdf → .docx | Best effort only | Lossy in every open-source tool |

Stirling-PDF's move away from LibreOffice toward its own converter, in beta since October 2026 ([Stirling-PDF releases](https://github.com/Stirling-Tools/Stirling-PDF/releases)), is a signal about the operational cost of bundling LibreOffice. Detecting a system install and offering it as optional is the lighter design. Offline proofing layers the same way: Harper (Apache-2.0, English only) lints in milliseconds via WebAssembly ([Harper](https://raw.githubusercontent.com/Automattic/harper/master/README.md)), with a Hunspell-dictionary library for other languages.

## Prior art proves the pattern; licences and churn carry the risk

### What already exists narrows the value proposition

ONLYOFFICE Desktop Editors 10.0, released in October 2026, already provides tabbed .docx, .xlsx, .pptx and .pdf editing offline for free ([ONLYOFFICE blog](https://www.onlyoffice.com/blog/2026/10/onlyoffice-desktop-editors-10)). Collabora Office does the same on the LibreOffice engine with a web UI. Stirling-PDF's desktop client, a Tauri app bundling a Java backend, shows that "web UI plus bundled heavy backend" packaging is maintainable by a small team. Several browser projects (ranuts/document, InledGroup/office, CryptPad) show third parties embedding the ONLYOFFICE editors with no document server. The research found no indie Electron or Tauri app wrapping these engines as a polished multi-format desktop tool, though absence from one search is weak evidence.

Two conclusions follow. First, a custom app cannot beat ONLYOFFICE Desktop on Office fidelity, because it would embed the same engine, slightly behind upstream. Its justification is the shell: Markdown, text and CSV as first-class peers, one palette, one safe pipeline with snapshots, a minimal interface, and room for personal features. Second, there is a legitimate smaller project: build the shell for .md, .txt, .csv and .pdf and hand .docx, .xlsx and .pptx to the installed suite. The roadmap should include an explicit checkpoint that compares the two before the Office integration begins.

### AGPL is free in private and decisive in public

| Component | Licence | Consequence |
|---|---|---|
| ONLYOFFICE editors, ranuts/document, x2t-WASM, Euro-Office | AGPL-3.0 with Section 7 terms | No obligation for private, undistributed use; the whole app must comply if distributed |
| SuperDoc, PPTist, MuPDF.js | AGPL-3.0 or commercial | Same; commercial pricing for SuperDoc was not found |
| Pandoc WASM, HyperFormula | GPL-2.0-or-later, GPL-3.0-only | Fine privately; a distribution constraint |
| LibreOffice, Collabora | MPL-2.0 | File-level copyleft; light even on distribution |
| CodeMirror, PDF.js, EmbedPDF, Papa Parse, IronCalc, Univer core, Electron | MIT / Apache-2.0 | Notices only |
| Univer Pro, EigenPal Pro, Handsontable, Polotno, tldraw | Commercial or source-available | Not open source; evaluation limits apply |

The AGPL permits making and running covered works that are not conveyed "without conditions" ([GNU AGPLv3](https://www.gnu.org/licenses/agpl-3.0.html)), so a personal, never-distributed build carries no source-publication duty. That reading is the researchers', not legal advice. The decision to build on ONLYOFFICE should be recorded as a standing constraint on ever publishing the app. ONLYOFFICE's licence is itself unsettled: version 9.4 in May 2026 reworded its additional terms ([ONLYOFFICE 9.4](https://onlyoffice.com/blog/2026/05/onlyoffice-docs-9-4)), and the Nextcloud and IONOS-led Euro-Office fork launched in March 2026 amid a dispute over the logo-retention term ([It's FOSS](https://itsfoss.com/news/onlyoffice-forked/); [Nextcloud blog](https://nextcloud.com/blog/euro-office-license-compliance-and-what-open-source-means)). Whether the logo obligation survives in the current text was not verified. Euro-Office's Document Server "is not a standalone application and needs a platform such as Nextcloud" ([Euro-Office DocumentServer](https://github.com/euro-office/DocumentServer)), so it is something to watch, not an embed target.

### The main risks, ranked by what they would cost

The first risk is **silent round-trip loss**. No candidate has an independent fidelity benchmark; the ONLYOFFICE-versus-LibreOffice ranking is reputation, SuperDoc's and EigenPal's preservation statements are vendor claims, and nobody verified how the WASM route handles VBA macros, tracked changes, comments, embedded fonts or password-protected files. An anecdotal report describes ONLYOFFICE stripping animations from a deck ([Nextcloud forum](https://help.nextcloud.com/t/nextcloud-or-onlyoffice-changes-my-animated-pptx-files/44796)).

The second is **dependence on community packaging**. The serverless ONLYOFFICE route rests on CryptPad's x2t build and a community wrapper, lags upstream, and has no published numbers for binary size, load time, memory or large-file limits. Pinning and vendoring a known-good build, with fonts and dictionaries, is the mitigation.

The third is **churn and boundary drift** in younger components: EmbedPDF v3 was two weeks old at research time, SuperDoc has changed repository names repeatedly, EigenPal moved review features to a paid tier within its first year, PPTist moved from Apache-2.0 to AGPL, and Quadratic's repository returned a 404 after reports it went closed-source ([Quadratic](https://github.com/quadratichq/quadratic)). The adapter boundary and version pinning contain this.

The fourth is **customisation resistance**. The ONLYOFFICE editors are canvas-rendered, minified and sparsely documented; hiding chrome and restyling through CSS is realistic, a fully custom toolbar or deep palette integration is not assured. Fonts are a cross-cutting fifth risk: substitute fonts change line breaks in every engine, and bundling metric-compatible fonts is the standard mitigation ([pptx-renderer](https://github.com/aiden0z/pptx-renderer)).

## Verify fidelity with a layered corpus harness before trusting any save

No ready-made open-source round-trip harness was found, so it has to be assembled, and it should exist before the Office engine is trusted with real files. One published methodology matches the needed layering: structurally diff input and output XML to quantify degradation, then measure layout by rendering headless PDF exports and running pixel comparison ([comparative study](https://akrillick.github.io/web/archive/A%20Comparative%20Study%20of%20OOXML%20and%20ODF%20Implementations.pdf)). Open-source projects already use the visual half; docxide-pdf scores output against Word-generated reference PDFs with Jaccard and SSIM metrics ([docxide-pdf](https://docs.rs/crate/docxide-pdf/0.8.0)).

For each corpus file and each engine, the harness opens and saves without edits, then applies four layers. The validity layer checks ZIP integrity, content types, relationship targets and schema conformance; the Open XML SDK validates OOXML but has no renderer ([Open XML SDK](https://github.com/dotnet/Open-XML-SDK)), and an Apache OpenOffice bug thread recommends running both the POI-based and Microsoft validators because each catches different errors ([AOO Bugzilla 124282](https://bz.apache.org/ooo/show_bug.cgi?id=124282)). Because files from the wild are often already non-conformant, the gate is "no new errors", not zero errors. The package layer lists parts added and removed and diffs canonicalised XML per part, reported as information, since engines legitimately rewrite most XML. The semantic layer extracts and compares content: text, styles, comment and tracked-change counts for documents; values, formulas, number formats, merges and defined names for workbooks; slide and shape counts, geometry and notes for decks; page count, text and annotation counts for PDFs. The visual layer renders original and output with the same pinned LibreOffice build and font set, rasterises pages and compares them with a pixel-diff tool such as pixelmatch ([pixelmatch](https://github.com/mapbox/pixelmatch)); using one renderer on both sides means differences reflect what the save changed. A fifth step repeats the run after a scripted small edit and asserts that the change is present and localised. For PDFs, `qpdf --check` supplies structural validation ([qpdf docs](https://qpdf.readthedocs.io/)), and annotations written by the app need manual cross-reader checks in Acrobat, Preview, Edge and Firefox, since no compatibility matrix exists and readers type each other's annotations inconsistently ([Zotero forums](https://forums.zotero.org/discussion/126434)).

The corpus should start with 30 to 50 of the developer's own real documents, the files that actually matter, then add feature coverage from Apache POI's test data ([POI test-data](https://apache.googlesource.com/poi/+/trunk/test-data/openxml4j)) and scale from a public corpus such as GovDocs1 ([Digital Corpora](https://digitalcorpora.org/corpora/file-corpora/files/)) for crash and timeout detection. It should deliberately include tracked changes and comments, fields and TOCs, SmartArt and charts, macro-enabled files, pivot tables and slicers, conditional formatting, embedded fonts, content controls, and signed and form-bearing PDFs. Markdown and text need only an idempotency test: open and save with no edits must be byte-identical. A small golden subset should be opened in Microsoft Office itself, because "file opens with a repair prompt" is the most damaging failure and validators catch it only partly.

End-to-end automation runs through Playwright's experimental Electron support, which launches the app and controls its windows ([Playwright Electron](https://playwright.dev/docs/api/class-electron)); whether it attaches to pages inside `WebContentsView` children without extra work was not confirmed. The harness's product-facing output is a per-format "safe to overwrite" status. Until a format passes the gates, the app defaults to saving a copy or backing up the original on first save.

## Conclusion

The brief's two headline requirements pull against each other, and the research makes the trade explicit: full feature breadth comes only from engines that regenerate files, while byte-level safety comes only from patch-in-place designs that are not yet mature. The workable resolution is to stop treating fidelity as a property of the editor and treat it as a property of the system: an engine chosen for breadth, wrapped by a pipeline that never destroys an original, and a corpus harness that converts "we hope it round-trips" into a measured, per-format status. That reframing also de-risks the engine choice itself, since an adapter boundary lets SuperDoc, a newer ONLYOFFICE build, Euro-Office or an in-place PPTX library replace the first choice as evidence arrives.

The open questions are all cheap to answer by experiment and none can be answered from published material: whether the ONLYOFFICE WASM build runs offline inside an Electron view from a custom protocol, what it costs in memory per tab and time per save, how much of its command surface a palette can reach, and how it and SuperDoc score against the personal corpus. A week of spikes should precede the architecture plan, and the plan should keep the smaller alternative on the table: a first-class Markdown, text, CSV and PDF app that hands Office files to an installed suite delivers most of the daily value at a fraction of the integration risk.
