# 0001 — How v0.1 of the Windows app was built

Date: 2026-11-22 · Status: accepted

The first build of Release 1 (Windows), in `apps/desktop`. This records where the build follows the plans, where it departs, and why.

## Follows the plan

- **Shell:** Tauri v2 on WebView2, Rust core, React + TypeScript interface (`12-platforms-and-mobile.md`).
- **Platform layer:** the interface never calls Tauri directly; everything goes through `src/platform` (an in-memory implementation runs the interface in a browser for tests).
- **Editor contract:** bytes in, bytes out; engines never touch the disk (`01-architecture.md`).
- **Text engine:** CodeMirror 6 for every text file, as decided for multi-device use (`06-code-and-text-editor.md`).
- **File pipeline:** atomic saves, auto-save for text formats, version snapshots kept outside the document folders (the first is always the original), crash recovery, external-change detection, encoding, BOM and line-ending preservation.
- **Two tiers:** the base app is small (installer about 5 MB); engines load only when a file of that type opens.
- **Verification:** unit tests for every byte-preservation rule, end-to-end tests named after the flow IDs in `docs/flows/`, and a self-test mode for the real app (`04-verification.md`).

## Departures

| Plan said | v0.1 does | Why |
|---|---|---|
| A pnpm workspace with one package per engine | One package with the same folders (`src/engines/*`, `src/lib`, `src/platform`) | Simpler build for one developer; the boundaries are kept by folders and the editor contract. Split later if needed |
| Office editing through the embedded ONLYOFFICE engine (W3) | Read-only previews of Word, Excel and PowerPoint | Spikes S1, S14 and S15 come first; previews make the app useful for Office files today |
| Version snapshots every save | At most one snapshot per file every 5 minutes while auto-saving (every 30 seconds for explicit saves) | Auto-saving every second would otherwise replace useful history with near-identical copies |
| PDF engine chosen by spike S6 (PDF.js or EmbedPDF) | PDF.js | Mature, permissive licence, and its built-in editors cover highlight, text and drawing; EmbedPDF remains the alternative |
| Drawn signatures stored encrypted | Stored as images in the app's data folder | Encryption needs a key-management decision; recorded as a gap |
| Native Mica title bar with snap layouts | Standard Windows title bar | Avoids losing the snap-layouts flyout; revisit in W6 |

## Review

An independent code review after the first build found ten bugs (recovered work could be marked saved after an undo, read-only files made tabs impossible to close, two tabs on one file could overwrite each other, a save during a PDF page operation could revert it, and others). All ten were fixed, with an end-to-end regression check for each data-loss case.

## How the Windows build is produced

- **GitHub Actions** builds natively on Windows (MSVC) and produces the installer and a single-file portable exe. Pushing a `v*` tag publishes them as a release.
- **Cross-compiling from Linux** (MinGW + NSIS) also works and was used during development. That build needs `WebView2Loader.dll` next to the exe, which the installer includes; its portable form is a zip of the exe and the DLL.
